# Clipboard Shelf v1.9.1 Step 0 — Historical Missing Image Asset Handling 设计

> 阶段：只读产品/架构设计（不改代码、不改 DB、不修改生产 config、不 commit/push/release）
> 基线：v1.9.0 已发布冻结（commit `0ef96c3`）

---

## 1. 背景与事实（生产只读取证，2026-08-14）

- 生产库 image item：**207 条**（`filePath` 非空）；full/thumb 文件存在：**2 条**；文件缺失：**205 条**（8/11 事故永久丢失，已接受恢复结果）。
- 205 条缺失记录中：**158 条保留 OCR 文本**；实体/现场/标注关联均为 **0**；sensitivity/metadataOnly 均为 0；annotations 总数 0。
- 这些记录剩余价值 = OCR 文本 + 来源/时间元数据 + 历史上下文；图片本体已不可恢复。
- 当前完整备份按「全有或全无」拒绝成功（v1.9.0 设计），生产冒烟已如实记录失败；DB-only 启动快照不受影响、始终可用。
- 这是**历史损坏状态**，不是 v1.9.0 新产生的问题。

---

## 2. 目标与约束

- 目标：让备份/校验/恢复在“存在已知历史缺失资产”时**可继续工作且语义诚实**，同时**完整保留历史记录**。
- 硬约束：不自动删除、不自动修复、不修改生产数据；设计阶段零代码。
- 用户立场：**不愿为了生成备份而盲目删除历史记录**。

---

## 3. 方案比较

### 方案 A：删除缺失 image item

| 维度 | 评估 |
| -- | -- |
| 数据损失 | **最大**：丢失 OCR（158 条）、时间/来源上下文、历史记录本身 |
| 可恢复性 | 图片本体已丢失，删除后连元数据也无法恢复 |
| 兼容性 | 高（backup 恢复全绿） |
| Backup 语义 | 回到“全资产完整” |
| Asset Integrity | 缺失归零（但等于“用删除掩盖问题”） |
| Entity/Worksite/annotations | 删除行会级联删除（当前缺失行无关联，影响小，但历史引用断裂） |
| 用户体验 | 违反用户明确意愿 |
| 实施复杂度 | 低（无 migration） |
| 是否需要 migration | 否 |

**结论：不推荐。** 违反“不盲目删除历史”的要求。

### 方案 B：保留 item + “已知缺失资产”状态，backup/verify 明确报告 incomplete

| 维度 | 评估 |
| -- | -- |
| 数据损失 | **无**（记录、OCR、元数据全保留） |
| 可恢复性 | 高（若文件找回可取消确认并恢复全资产状态） |
| 兼容性 | 高（新增列 additive，不改变 v1.9.0 现有行为） |
| Backup 语义 | 两级：全资产完整备份（SUCCESS）／当前状态一致备份（SUCCESS but incomplete，manifest 显式列出确认缺失） |
| Asset Integrity | 区分 UNEXPECTED_MISSING（state=ok 但缺文件，可操作）与 PERMANENT_MISSING（state=missing，信息性） |
| Entity/Worksite/annotations | 完全保留，恢复后一致 |
| 用户体验 | 历史记录照常可看；巡检/备份给出明确但非阻断的状态 |
| 实施复杂度 | 中（migration v5 additive + backup/verify/integrity/UI 分支） |
| 是否需要 migration | 是（additive，无数据改写） |

**结论：推荐主方案。**

### 方案 C：将缺失图片记录降级为 OCR/文本历史记录

| 维度 | 评估 |
| -- | -- |
| 数据损失 | 中：丢失“这是现场图片”的语义、原文件元数据（尺寸/大小/路径）；type 改写 |
| 可恢复性 | 低（若文件找回难以重新挂载为图片） |
| 兼容性 | 中（列表渲染、输出、FTS 行为变化；历史引用语义改变） |
| Backup 语义 | 恢复“全资产”通过（因为不再引用文件） |
| Asset Integrity | 缺失消失（掩盖而非记录） |
| Entity/Worksite/annotations | 可保留（按 item_id），但“图片”身份丢失 |
| 用户体验 | 历史里看到的是文本而不是“缺失照片”，可能误导 |
| 实施复杂度 | 中高（类型改写 + 字段迁移 + 输出/检索适配） |
| 是否需要 migration | 是（数据改写型，更重） |

**结论：不推荐为首选；可作为 B 的补充视图（例如 UI 把“缺失图片的 OCR”展示为文本摘要），但不应改写数据。**

### 方案 D：其他

- **D1：独立资产注册表 / asset-state 模型 + 重挂载支持**（每资产行记录 path/type/hash/state/confirm 时间）：最完整，支持“文件找回后重挂载”，但复杂度最高，建议作为 **v1.9.2+ backlog**。
- **D2：备份增加 `--allow-incomplete` 临时开关（无持久状态）**：零 migration，但每次都要显式选择、且无法区分“已知永久缺失”与“意外缺失”，不能回答 Asset Integrity 的语义问题。可作为 B 的过渡（B-light）。
- **D3：保持现状 + 文档化**：不解决任何问题。

**结论：B 为推荐，D2 可作为 B 未落地前的临时逃生通道（可选），D1 作为后续演进。**

## 4. 推荐方案（B）

> 保留 205 条历史记录；新增**显式、可逆的“确认永久缺失”状态**；备份/校验/恢复按两级语义工作。

### 4.1 数据模型（migration v5，additive）

```sql
ALTER TABLE items ADD COLUMN assetState TEXT NOT NULL DEFAULT 'ok';      -- 'ok' | 'missing'
ALTER TABLE items ADD COLUMN assetMissingAt INTEGER;                     -- 确认时间
ALTER TABLE items ADD COLUMN assetMissingNote TEXT;                      -- 原因备注（如：8/11 事故丢失）
```

- 不建新表；不加实体表；不加新依赖。
- 默认 `'ok'`：现有行为完全不变（缺失=意外缺失=阻断完整备份）。
- 205 条记录**不自动标记**；必须由用户在巡检后显式“确认永久缺失”。

### 4.2 Backup 语义（两级 + DB-only）

| 备份类型 | 触发 | 判定 |
| -- | -- | -- |
| DB-only 快照（现有启动备份） | 启动 | 永远成功（不依赖图片文件） |
| 完整备份（全资产） | 手动/每日 | 所有引用文件存在 → `SUCCESS` |
| 完整备份（当前状态一致） | 同上 | 引用文件要么存在、要么 `assetState='missing'` 被确认 → `SUCCESS (incomplete)`，manifest 显式列出 missingAssets |
| 拒绝条件 | 同上 | 存在 `assetState='ok'` 但文件缺失 → `FAIL`（现状保持） |

Manifest 增加（向后兼容，旧 manifest 无此字段视为全资产）：

```json
{
  "assetState": "complete" | "incomplete",
  "missingAssets": [
    { "itemId": 168, "kind": "full", "file": "1782150277152_a3b1iz.png", "confirmedAt": 1786... }
  ]
}
```

### 4.3 Verify 报告语义

- 全资产备份 → `VERIFY: PASS (complete)`
- 当前状态一致备份 → `VERIFY: PASS (consistent, N known missing)` —— 不是失败
- manifest 与实际不符（新增意外缺失/文件出现但状态仍 missing）→ `VERIFY: FAIL` + 差异清单

### 4.4 Restore 语义

- 恢复时 `assetState` 随 DB 还原；
- staging 校验把“确认缺失”视为**有效状态**（不再要求全资产存在）；
- 恢复后完整性检查只要求：无 `assetState='ok'` 的文件缺失（无新增意外缺失）；
- 若确认缺失的文件在恢复后被找回 → 提示可“解除确认”（不自动改状态）。

### 4.5 Asset Integrity 分类

| 分类 | 判定 | 可操作性 |
| -- | -- | -- |
| UNEXPECTED_MISSING | `assetState='ok'` 且文件缺失 | 可确认 / 可恢复文件 / 可清理 |
| PERMANENT_MISSING | `assetState='missing'` 且文件缺失 | 信息性（默认不告警、不阻断） |
| RECOVERED | `assetState='missing'` 但文件重新存在 | 提示可解除确认 |

巡检报告继续只读；默认只把 UNEXPECTED_MISSING 作为问题项。

### 4.6 用户操作（显式、二次确认）

设置 → 资产一致性巡检 → 缺失清单：

- 「确认永久缺失（保留历史记录）」：二次确认后写入 `assetState='missing'` + 时间 + 备注；**可逆**（「解除确认」）。
- 不做批量自动确认；确认操作本身写入 backup-log 审计条目。

## 5. 十个关键问题（逐答）

1. **205 条记录是否应该删除？** 不应该。它们保留 OCR/来源/时间历史；删除将永久丢失唯一剩余价值，且违反用户意愿。
2. **如何保留 OCR/entity/历史上下文？** 全部原样保留；推荐方案不改变数据，仅在 `items` 增加确认状态列。
3. **Backup 在存在历史缺失资产时应该 FAIL / PARTIAL / DB-only？** 采用三级语义：DB-only 永远成功；**已确认缺失**时完整备份为 `SUCCESS (incomplete)`（不是 PARTIAL 半成品，是“当前状态一致”的完整快照）；**未确认的意外缺失**时 FAIL（保护完整性）。
4. **如何定义“完整备份”和“当前状态一致备份”？** 完整备份 = 引用文件全部存在；当前状态一致备份 = 引用文件全部存在或被确认缺失，manifest 显式记录缺失清单。两者都是“成功”，状态字段区分。
5. **Asset Integrity 如何表达永久缺失 vs 暂时缺失？** 通过 `assetState`：`ok` + 缺文件 = UNEXPECTED_MISSING（暂缺/异常）；`missing` + 缺文件 = PERMANENT_MISSING（已知）；`missing` + 文件出现 = RECOVERED。
6. **Verify 如何报告？** `PASS (complete)` / `PASS (consistent, N known missing)` / `FAIL + 差异清单`。
7. **Restore 如何处理已知缺失资产？** 原样恢复状态与现有文件；校验只要求无新增意外缺失；已确认缺失保持缺失。
8. **以后如何避免这种状态再次阻断全部备份？** 三层保障：DB-only 快照永远独立可用；完整备份仅在“未确认的意外缺失”时失败；巡检 + 显式确认让历史损坏可被记录后不再阻断。可选 D2 临时开关作为兜底。
9. **是否需要统一 assetStatus/assetState 模型？** 需要，但**最小化**：`items.assetState`（ok/missing）即可满足 v1.9.1；完整“资产注册表/每资产状态”属于 D1，留 v1.9.2+。
10. **是否应该支持“确认永久缺失”操作？** 应该，且必须显式、二次确认、可逆；默认不自动确认任何记录。

## 6. 实施范围建议（v1.9.1 MVP，仅设计，不实施）

- migration v5：`items.assetState / assetMissingAt / assetMissingNote`（additive、幂等、回滚=删列）；
- backup-service：manifest 增加 `assetState/missingAssets`；创建与验证按两级语义；拒绝条件=存在意外缺失；
- asset-integrity：新增 UNEXPECTED_MISSING / PERMANENT_MISSING / RECOVERED 分类；
- IPC/UI：巡检缺失清单 + 「确认永久缺失 / 解除确认」（二次确认）；
- restore 校验：按状态语义放宽（确认缺失视为有效）；
- 测试：migration 幂等、backup complete/incomplete/FAIL、verify 三态、restore 保持状态、integrity 三分类、UI 确认/撤销、回归 242+。

## 7. 不做什么

- 不自动删除、不自动修复、不自动标记；
- 不把 205 条记录改写为文本（方案 C 只做视图层可选，不改数据）；
- 不做资产注册表/重挂载（D1 留 v1.9.2+）；
- 不修改 v1.9.0 的「全有或全无」默认语义（仅当资产被确认缺失时放宽）；
- 不改生产数据、不 commit/push/release。

---

## 8. 风险

| 风险 | 缓解 |
| -- | -- |
| 用户误点“确认永久缺失” | 二次确认 + 可逆 + 审计日志 |
| 确认后文件找回却被当缺失 | RECOVERED 分类提示解除确认 |
| manifest 版本兼容 | 旧 manifest 无新字段视为 complete；读取兼容 |
| 迁移破坏 | additive 列 + 幂等 + 可回滚 |
| 完整备份仍被其他原因阻塞 | 保持 fail-fast；DB-only 兜底 |

---

## 9. 最终推荐

**推荐方案 B**：

```text
保留全部历史记录
  + items.assetState（ok/missing，additive migration v5）
  + 显式「确认永久缺失」（可逆、二次确认、审计）
  + 完整备份 = SUCCESS(complete) | SUCCESS(incomplete) | FAIL(意外缺失)
  + Verify = PASS(complete) | PASS(consistent, N known missing) | FAIL(差异)
  + Asset Integrity = UNEXPECTED_MISSING / PERMANENT_MISSING / RECOVERED
  + Restore = 保持状态 + 只校验无新增意外缺失
```

该方案零数据损失、不改变 v1.9.0 默认语义、对 205 条历史记录零改动（仅允许用户显式标记），并让生产在标记后可恢复“完整备份可用”。
