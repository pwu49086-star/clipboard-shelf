## 1. 当前 backup 架构（代码实查）

现状实现（`src/main/services/db-service.js`）：

- **时机**：仅 `init()` 启动时、打开 DB **之前**执行一次 `backupDatabase()`；无定时、无关闭备份；
- **内容**：`fs.copyFileSync(shelf.db → backups/shelf-<ts>.db)` + `fs.copyFileSync(config.json → config-<ts>.json)`；
- **保留**：`shelf-*.db` 保留最近 5 份；`config-*.json` **不清理**（生产已积累约 90 份）；
- **范围**：不含 `images/`、`pet-tasks.json`、`encryption.json`；
- **一致性**：裸拷贝主 DB 文件，**不复制 WAL/SHM、无 checkpoint**；
- 生产实测（2026-08-14）：`journal_mode=wal`，`synchronous=2(NORMAL)`，page_count=5858，page_size=4096；`shelf.db-wal` 约 4.3 MB 未落盘——若此刻启动备份，最近事务将不进备份。

**结论**：当前“备份”只是启动快照，既不是完整备份，也不保证一致。

## 2. SQLite 一致性（重点）

### 事实

- `better-sqlite3` v12.11.1，提供官方 **Online Backup API**：`db.backup(filename, { progress })`（`lib/methods/backup.js`，异步、支持进度回调）；
- 生产与测试 DB 均为 `journal_mode=wal`（init 时设置，WAL 是持久模式）；
- 应用为**单连接**长驻（`db-service` 全局 `db`），无第二连接、无长事务；查询为同步 better-sqlite3 调用，无长 reader；
- `db.close()` 在 `will-quit`（index.js:838）与 uncaughtException（index.js:92）执行；应用内无其他 checkpoint 调用；
- 图片写入、标注写入、retention 删除均可能在备份期间发生（异步捕获 + 同步 unlink）。

### 方案比较

| 方案 | 一致性 | WAL 安全 | 运行中安全 | 性能 | better-sqlite3 兼容 | 恢复兼容 | 结论 |
| -- | -- | -- | -- | -- | -- | -- | -- |
| A. Online Backup API（`db.backup()`） | 高（SQLite 官方快照，含 WAL 事务） | 是 | 是 | 高（增量页复制 + 进度回调） | **直接可用（v12 已内置）** | 产出标准 SQLite 文件 | **推荐** |
| B. checkpoint 后复制 | 中高（`PRAGMA wal_checkpoint(TRUNCATE)` 后拷主文件） | 依赖 checkpoint 成功 | 是（但 checkpoint 可能 busy） | 高 | 需要 `db.pragma` 手动调用 | 标准文件 | 备选，不推荐主用 |
| C. 应用级写暂停 | 高 | 是 | 侵入性大 | 中 | 无原生支持 | 标准文件 | 不推荐（复杂度/崩溃恢复） |
| D. DB+WAL+SHM 成套复制 | **低**（活库文件级复制非一致快照） | 否 | 否（Windows 文件锁） | 中 | 无 | 依赖 sidecar，非便携格式 | 不推荐 |

### 推荐方案 A：better-sqlite3 Online Backup API

理由：
1. SQLite 官方机制，快照天然包含 WAL 中已提交未 checkpoint 的事务；
2. 应用运行期间安全，不需要暂停任何写入；
3. 异步 + `progress` 回调，可量化进度、可取消；
4. 产物是标准 SQLite 文件，恢复兼容性最好；
5. 零新依赖、零新 schema。

不选 B：`wal_checkpoint(TRUNCATE)` 在活跃写入下可能返回 busy，且 checkpoint 与复制之间仍有窗口；正确性依赖手工编排，收益低于 A。
不选 C：需要给 clipboard-pipeline / entity job / annotations:save / retention / notes 全部加写闸，崩溃恢复复杂，UI 卡顿风险；A 无此必要。
不选 D：活库的 db/wal/shm 三件套不是一致快照，Windows 上主文件被进程占用不可复制，且不是可移植备份格式。

实现要点（设计）：
- `db.backup(tmpDbPath, { progress })` 写入临时文件；
- 完成后对临时 DB 做只读打开 + `PRAGMA integrity_check` + 计数抽样；
- 再复制 config/pet-tasks/encryption.json（小文件，直接拷贝 + 校验）。

## 3. 图片资产一致性

### 问题

DB 快照与文件资产之间存在竞态：
- 捕获流程：写 full → 写 thumb → DB insert（写文件与 commit 之间崩溃会孤儿）；
- 删除/retention：删行 → unlink（unlink 失败静默 → 行无文件；unlink 成功而删行前崩溃 → 文件无行）；
- 备份期间可能同时发生上述写入/删除。

### 设计：快照枚举 + 全有或全无

1. **先取 DB 快照**（Online Backup API）→ 快照定义备份时间点 T0；
2. **从快照 DB（只读打开临时副本）枚举**所有需要备份的文件：
   - `items.filePath`（full）、`items.thumbPath`（thumb）、`items.annotatedPath`（annotated，非空时）；
3. **复制资产**：逐个按快照清单流式复制；复制时记录 size；
4. **哈希校验**：对每个已复制文件计算 sha256，与复制后文件核对；缺失/尺寸不符 → 本轮失败；
5. **并发删除兜底**：若快照清单中的文件在复制时已不存在（T0 后被 retention/删除移除），**整轮失败并重试一次**（重新取快照）；重试仍失败 → 报告失败原因，不产生“成功”备份；
6. 快照之后新建的图片**不要求**出现在本轮（下次备份覆盖），保证 manifest 与快照严格一一对应。

> 一致性关系：**manifest 的 images 列表 = 快照 DB 中所有图片行引用的文件**，且每个文件已验证存在 + 哈希一致。这就是“DB snapshot ↔ image asset snapshot”的建立方式。

## 4. Integrity Manifest 设计

实际最小结构（不照抄建议模板，去掉冗余）：

```json
{
  "format": "clipboard-shelf-backup",
  "version": 1,
  "backupId": "2026-08-14T06-00-00-000Z",
  "createdAt": 1786888800000,
  "appVersion": "1.9.0",
  "schemaVersion": 4,
  "db": {
    "file": "shelf.db",
    "sha256": "…",
    "size": 23461888,
    "pageCount": 5858,
    "integrityCheck": "ok"
  },
  "extra": [
    { "file": "config.json", "sha256": "…", "size": 319 },
    { "file": "pet-tasks.json", "sha256": "…", "size": 296 },
    { "file": "encryption.json", "sha256": "…", "size": 55 }
  ],
  "images": [
    { "path": "full/1786xxx.png", "itemId": 1234, "sha256": "…", "size": 12345, "mtime": 1786888000000 }
  ],
  "counts": {
    "items": 2717, "images": 207, "entities": 1839,
    "annotations": 0, "worksites": 0, "notes": 0
  },
  "success": true
}
```

字段决策：
- `relativePath` / `size` / `sha256` / `mtime`：**全部保留**。sha256 是权威校验，size 快速预检，mtime 供诊断；
- `itemId`：**保留**。恢复验证需要“行 ↔ 文件”映射，也是未来孤儿文件重新挂载的输入；
- `type`：不需要（子目录 full/thumb/annotated 即类型）；
- `annotationId`：不需要（annotated 文件名含 `itemId_<ts>.png`，按 itemId 关联）；
- `worksiteId`：不需要（Worksite 关联在 DB 内，恢复后自然成立）；
- `schemaVersion`：**必须**（恢复兼容性判断）；
- `success: true`：**必须**（只有最终校验通过才写入；半成品目录不生成或标记失败）。

**隐私红线：manifest 不得包含正文、OCR 原文、实体值、来源应用等任何内容字段**——只含文件名、哈希、尺寸、时间、id。

## 5. Backup Format

比较：

| 格式 | 可靠性 | 备份速度 | 恢复速度 | 文件大小 | Windows 文件锁 | 损坏检测 | 用户可理解 | 增量空间 |
| -- | -- | -- | -- | -- | -- | -- | -- | -- |
| A. 整目录快照 | 高 | 快（流式复制） | 快 | 中（≈资产总大小） | 低（不碰活文件，只读复制） | manifest | 高 | 高（按目录/文件增量） |
| B. 单一 ZIP archive | 中高 | 慢（压缩） | 中（需解压） | 低 | 低 | archive CRC + manifest | 中 | 低（重打整包） |
| C. DB + assets 分离 | 高 | 快 | 快 | 中 | 低 | manifest | 中 | 高 |

**推荐 A：整目录快照（两阶段原子化）**：

```text
backups/
  <backupId>.tmp/          ← 写临时目录
    shelf.db
    config.json
    pet-tasks.json
    encryption.json        （如存在）
    images/full|thumb|annotated/...
    manifest.json
  <backupId>/              ← 校验通过后 rename 为正式目录
```

- 备份写入 `.tmp`，成功后**原子 rename** 为正式目录；半成品不会伪装成成功备份；
- 每次完整备份是**独立快照**，与当前 images 目录无共享可变状态（后续增量优化时再引入硬链接/去重，v1.9 不做）；
- ZIP（B）作为 P2 的“便携导出”附加能力，不做主格式；
- C 与 A 实质相同（A 内部即 db/config/images 分目录），统一采用 A。

## 6. Backup Lifecycle

### 两级备份

| 类型 | 触发 | 内容 | 保留 |
| -- | -- | -- | -- |
| 快速启动备份（DB-only） | 应用启动时（保留现有语义） | DB 一致快照 + config + pet + encryption | 5 份 |
| 完整备份 | 手动“立即备份” + 每日一次（当日无完整备份时）+ 版本升级前（package version 变化时） | DB + config + pet + encryption + 全部图片 + manifest | **默认 3 份**（可配置 1–10） |

保留策略：按 `createdAt` 排序，超额删除最旧；删除前先校验目标目录是 `backups/<backupId>` 完整格式，防止误删。

### 成功标准（明确）

```text
DB snapshot（integrity_check ok）
+ assets copied（快照枚举全部命中）
+ manifest generated
+ manifest verified（DB hash + 每文件 hash 复验）
+ 原子 rename
= SUCCESS
```

任一环节失败 → 整体 FAILED：清理 `.tmp`，写入 `backups/backup-log.json`（时间/类型/结果/失败阶段/错误），UI 展示最后成功时间与失败原因。

### 失败与异常处理

- **磁盘不足**：备份前预检（预估 = DB 大小 + images 总大小 + 20% 余量 + 10MB），不足即失败，**不写半成品、不碰生产**；
- **图片复制失败/缺失**：整轮失败 + 重试一次（重新快照）；重试失败 → 明确报告；
- **manifest 生成失败**：失败，不 rename；
- **中断恢复**：下次启动/下次备份时扫描并清理超过 24h 的 `*.tmp` 目录；
- **校验失败**：保留失败目录 24h（便于诊断），记录日志，不计入“成功备份”；
- 备份全程**只读当前生产数据**（DB 用在线备份、图片只读复制），失败不可能破坏生产。

## 7. Recovery Flow

```text
选择 backup（UI 或 --restore=<path>）
  ↓
① 验证 manifest（格式/版本/DB hash/文件 hash/计数）
  ↓
② 验证 DB（只读打开 + integrity_check + schemaVersion ≤ 当前）
  ↓
③ 验证图片（每个 image row 的 full/thumb/annotated 存在）
  ↓
④ 二次确认（输入“RESTORE”或勾选确认框）
  ↓
⑤ 自动创建当前环境回滚点（backups/pre-restore-<ts>/，DB+config+pet+encryption+images 复制）
  ↓
⑥ 关闭应用数据层（停止 pipeline/retention/OCR → db.close()）
  ↓
⑦ 恢复到 staging 目录（解包/复制到 userData 同级 staging）
  ↓
⑧ 再次验证 staging（同 ①-③）
  ↓
⑨ 原子替换（userData → userData.old；staging → userData）
  ↓
⑩ app.relaunch()（启动后自动跑完整性检查；失败则自动回退 userData.old）
```

规则：
- **应用运行中禁止直接覆盖**：必须走 ⑥⑨⑩（关闭 → 替换 → 重启）或 `--restore` 启动参数（启动早期、DB 打开前执行）；
- 恢复前自动回滚点 = 恢复本身的第一道保险；
- 半恢复状态避免：先 staging 验证再替换；替换用目录级 rename（同卷），失败回退；
- 回滚点保留到下次成功启动后清理（保留 1 份）。

## 8. Restore Validation

恢复后（应用启动内）自动运行：

```text
DB 可读（integrity_check）
items 数量 == manifest.counts.items
images 行数量 == manifest.counts.images
entities / annotations / worksites / notes 数量 == manifest.counts
FTS 可查询（SELECT count FROM items_fts）
每个 image row：full 存在、thumb 存在、annotated 存在（若 annotatedPath 非空）
每个 annotation：item 存在、annotated 文件存在（若 annotatedPath 非空）
扫描：MISSING_FILE / ORPHAN_FILE / MISSING_ANNOTATED / ORPHAN_ANNOTATED / HASH_MISMATCH（对照 manifest）
retention 配置可读
```

任一失败 → 提示 + 自动回退到 `userData.old`（若已建立）。

## 9. Version Compatibility

- **v1.8 → v1.9**：schema 不变（v4），直接恢复；
- **更旧版本（v1.7/v3、v1.6/v2、v1.5/v1）**：**允许恢复**。备份原样保存旧 schema 的 DB；恢复后应用启动时执行现有幂等 migration（已实测 v1→v4 / v2→v4 / v3→v4 均无损），迁移前自动做启动备份；
- **拒绝规则**：manifest.schemaVersion > 当前支持版本 → 明确提示“备份来自更新版本”，不覆盖；manifest 缺失/损坏 → 拒绝恢复；
- 备份本体永不“升级改写”，保留原样（历史快照语义）。

## 10. Encryption

- 备份**原样保存加密状态**：DB 内容已加密则备份文件即加密内容；`encryption.json` **必须随备份复制并纳入 manifest**（缺失时恢复后无法解锁）；
- 不要求明文备份、不要求主密码参与备份（本地场景：主密码保护的是内容本身，备份文件与生产同权）；
- 恢复后 locked/unlocked 状态与备份时一致；恢复验证不尝试解密内容（只验证结构）；
- **manifest 隐私红线**：不含正文/OCR/实体/来源；哈希与文件名不构成内容泄露；
- 备份目录本身**默认不加密**（与生产 userData 同权限假设）；若未来支持 ZIP 导出，密码加密作为可选 P2，默认不开启。

---

## 11. Worksite

- 关联全部在 DB：`worksites` 表 + `items.worksiteId` + `annotations.item_id`；
- 完整备份 = DB 快照（含全部关联）+ 被引用图片；恢复后 `worksite → item → image → annotation` 自动重新成立；
- manifest.counts 校验覆盖 worksites/annotations 数量；恢复验证按 `annotatedPath` 检查文件存在；
- 无需新字段、无需多归属（保持轻量单归属，与 Step 0 结论一致）。

---

## 12. Backup 与 Retention 的关系

**保证：retention 不会影响历史备份。**

- 每次完整备份是独立目录、只读快照；备份创建后不与当前 images/DB 共享任何可变状态；
- retention/delete 只作用于当前 userData；
- Day1 备份（1000 items）在 Day2 retention 清理 100 条后**仍保留 1000 条**；
- 唯一交互点：备份进行中 retention 删除文件 → 由 §3 的“重试/失败”策略处理，绝不产生半成品成功备份。

## 13. Asset Integrity（P1，独立只读设计）

形态：
- 独立只读诊断模块（service + IPC + 设置面板入口），**不自动删除、不自动修复**；
- 输入：当前 userData 的 DB + images 目录（或指定备份目录）；
- 输出五类清单：

```text
MISSING_FILE        行有、文件无
ORPHAN_FILE         文件有、行无
MISSING_ANNOTATED   annotation/annotatedPath 有、annotated 文件无
ORPHAN_ANNOTATED    annotated 文件有、无引用
HASH_MISMATCH       文件 hash/size 与记录不符（有基线时；当前无基线则输出 size/mtime 差异）
```

- 生产预期首跑输出（与 Step 0 实测一致）：`205 MISSING_FILE / 9 ORPHAN_FILE / 0 / 0 / 0(HASH 无基线)`；
- 报告可导出 JSON；恢复工具中的“孤儿文件重新挂载”为独立 P2 动作，默认关闭；
- 性能：仅扫描 images 目录 + 单表查询，5000 items / 数千图片 < 2s；
- 与 Backup 复用 manifest 校验器（同一套 hash/枚举代码）。

## 14. Delete Safety（P1）

现状：unlink 永久、失败静默、无 dry-run。

方案比较：

| 方案 | 实现成本 | 数据安全 | 磁盘成本 | 用户体验 | 结论 |
| -- | -- | -- | -- | -- | -- |
| A. 继续永久删除 | 0 | 低 | 0 | 现状 | 不作为目标 |
| B. Trash / Recycle Bin（`shell.moveItemToTrash`） | 低 | 高 | 低（系统回收站） | 原生可恢复 | **P1 候选（性价比最高）** |
| C. 软删除 + 延迟清理 | 中 | 高 | 中 | 需 UI | P2 候选 |
| D. 删除前快照 | 中 | 高 | 中 | 自建恢复 | P2 候选 |

**v1.9 必须做（最小）**：
1. 所有图片 unlink 失败写日志（不再静默）；
2. retention / clearNonFavorites / cleanByPolicy 支持 **dry-run**（输出将被删除清单，不执行）；
3. 删除入口显示“将永久删除图片”的明确文案（现状 UI 已带确认，需补充图片数量提示）。

**v1.9 不强制实施回收站**：完整备份已提供恢复兜底；回收站化（B）列为 P1.1/P2，由用户决策后再做，避免改变删除语义。

## 16. Performance Targets（量化）

### DB snapshot（Online Backup API）

```text
当前生产 DB ≈ 23 MB
P95 < 1s
max < 3s
```

### 图片备份（本地 SSD，平均 ~0.5 MB/张，复制 + sha256 单次遍历）

| 规模 | 总耗时目标 | CPU | IO | UI |
| -- | -- | -- | -- | -- |
| 100 张 | < 2s | 低 | 中 | 不卡（异步 + progress） |
| 500 张 | < 8s | 中 | 中高 | 不卡 |
| 1000 张 | < 15s | 中 | 高 | 进度条 |

### 恢复

```text
1000 张 + 23MB DB：staging 复制 + 校验 < 30s
原子替换 < 5s
启动完整性检查 < 3s
```

约束：备份/恢复全程异步，不阻塞 clipboard pipeline；哈希计算单线程即可满足目标，无需 worker 线程（v1.9 不引入）。

## 17. Backup UI（简单，不做云盘）

```text
设置 → 备份与恢复
  ├─ 最后成功备份：时间 / 大小 / 图片数 / 校验状态
  ├─ 立即备份（按钮 + 进度）
  ├─ 最近备份列表：时间 / 类型（完整/快速）/ 大小 / 状态（成功/失败原因）
  ├─ 验证（选中备份 → 校验 manifest + DB + 图片）
  ├─ 恢复（选中备份 → 二次确认 → 自动执行 §7 流程）
  └─ 保留数量设置（完整备份 1–10，默认 3）
```

失败原因以纯文本展示；不做后台任务中心。

## 18. Failure Handling（汇总）

| 故障 | 行为 |
| -- | -- |
| 磁盘不足 | 预检失败，不写任何文件，提示 |
| DB backup API 失败 | 清理 tmp，记录日志，保留旧备份 |
| 图片缺失/复制失败 | 整轮失败 + 重试一次；重试失败报告 |
| manifest 生成/校验失败 | 失败，不 rename |
| 备份中断（强杀） | 下次启动清理 >24h 的 *.tmp |
| 恢复验证失败 | 阻止替换；提示原因 |
| 替换后启动失败 | 自动回退 userData.old |
| 旧版本备份 | schemaVersion 兼容则恢复后自动迁移；更高版本则拒绝 |
| 校验失败目录 | 保留 24h 供诊断，不计入成功备份 |

## 19. Tests

1. 备份-恢复 roundtrip（TEST_ROOT：造数据 → 备份 → 清空 → 恢复 → 全绿）；
2. manifest 校验注入（DB 改一字节 / 删一张图 / 改 size → 恢复被拒）；

## 20. v1.9 MVP（重新评估后）

按数据风险重新排序，**维持 Step 0 结论但调整边界**：

```text
P0   Backup & Recovery（完整备份 + 恢复 + 验证 + 回滚点）
P1   Asset Integrity（只读诊断，与 Backup 共用校验器）
P1   破坏性操作加固（unlink 失败日志 + dry-run + 删除文案）
P1.1 图片回收站化（shell.moveItemToTrash，等 P0/P1 验收后再定）
P2   图文 Markdown / ZIP 便携导出 / Worksite 增强 / Entity 增强
```

理由：Backup 是事故根因的直接解；Asset Integrity 是“备份是否有意义”的验证基础（二者共享 manifest/枚举代码，成本合并）；破坏性操作加固是低成本高风险缓解；图文 Markdown 仍高价值但数据安全优先。

## 22. 风险

| 风险 | 等级 | 缓解 |
| -- | -- | -- |
| 恢复误覆盖生产 | 高 | 二次确认 + 自动回滚点 + staging 验证 + 失败自动回退 |
| 备份中途 retention 删文件 | 中 | 快照枚举 + 全有或全无 + 重试一次 |
| 图片量大磁盘翻倍 | 中 | 保留 3 份默认 + 可配置 + 磁盘预检 |
| 旧版本备份迁移失败 | 低 | 现有幂等 migration + 迁移前启动备份 |
| encryption.json 缺失 | 高 | 纳入 manifest 强校验，缺失即恢复失败提示 |
| 备份性能影响日常使用 | 低 | 异步 + 后台 + 进度；启动备份仅 DB-only |
| manifest 泄露 | 低 | 不含内容字段，仅文件名/hash/id |

## 23. 最终推荐

1. **SQLite 一致性**：采用 better-sqlite3 Online Backup API（方案 A）；
2. **图片一致性**：DB 快照优先 + 快照枚举 + 复制 + hash 校验 + 全有或全无；
3. **备份格式**：整目录快照（`.tmp` → 原子 rename），manifest 为唯一校验入口；
4. **成功标准**：DB + assets + manifest + 复验 + rename 全部完成才算成功；
5. **恢复**：验证 → 回滚点 → 关闭数据层 → staging → 验证 → 原子替换 → 重启 → 完整性检查 → 失败自动回退；
6. **兼容性**：允许旧版本备份恢复 + 启动自动迁移；更高版本拒绝；
7. **加密**：原样备份（含 encryption.json），不要求明文/密码；manifest 隐私最小化；
8. **删除安全**：先做 dry-run + 失败日志；回收站化留 P1.1/P2；
9. **MVP**：P0 Backup & Recovery + P1 Asset Integrity + P1 破坏性操作加固；
10. **纪律**：全部实现只允许在 TEST_ROOT 验证；不 commit/push/release 直到用户批准实施。
