# Clipboard Shelf v1.5 架构规划

> 状态：Research / Architecture / Product Planning（只规划，不实现）
> 基线：v1.4.1（已发布、已冻结、稳定运行）
> 本文档基于对当前代码的实际阅读编写，不假设架构。

---

## 1. v1.5 产品目标

暂定定位升级为：

> **Clipboard Shelf —— 理解用户正在处理什么的本地工作上下文助手**

不做“功能堆叠”，而是在现有“记录 → 搜索 → AI 动作”之上，增加一条轻量的闭环：

```text
内容理解 → 上下文识别 → 本地资料联想 → 快速动作
```

本阶段只做三个能力：

- P0-1 本地实体识别（本地规则，不依赖 AI）
- P0-2 复制即联想（高置信度、低打扰提示）
- P1 本地维修资料索引（第一阶段只索引文件元数据，不做 RAG）

成功标准不是功能多，而是：

- 高频、低打扰；
- 复制后不卡顿；
- 敏感内容不因新能力泄露；
- 联想“宁可少提示，也不能骚扰”。

## 2. 用户工作流

### 2.1 当前工作流（v1.4.1）

```text
复制（Chrome/微信/IMA/Explorer/维修软件）
  → 1s 轮询检测
  → source snapshot（检测点）
  → 去重 → 队列 → 落库（sensitivity/metadataOnly 门禁）
  → UI 列表 + 宠物反馈 + OCR（图片）
  → 搜索（FTS5/LIKE）→ 复制/收藏/编辑
```

### 2.2 目标工作流（v1.5）

```text
复制“大金 RXYQ16AYM U4”
  → 正常落库（主链路完全不变）
  → 异步实体识别（brand=大金 / model=RXYQ16AYM / fault=U4）
  → 异步本地资料匹配（文件名索引）
  → 高置信度时出现轻提示：“🔧 找到 3 份相关资料”
  → 点击 → 打开本地文件
```

### 2.3 典型场景（HVAC 维修）

1. 从维修软件/聊天中复制故障文本 → 列表正常记录，后台识别出品牌/型号/故障码；
2. 识别命中高置信度时提示本地手册（如 `U4故障处理.pdf`、`RXYQ系列维修手册.pdf`）；
3. 用户点击打开文件，或忽略；忽略行为进入冷却，不重复骚扰；
4. 用户之后在历史记录中搜索时，可通过实体（品牌/型号/故障码）快速过滤。

## 3. 现有架构盘点（基于 v1.4.1 实际代码）

### 3.1 主进程结构

`src/main/index.js` 是唯一入口，职责：

- 创建主窗口/宠物窗口、托盘、全局快捷键；
- 初始化并接线服务：db、clipboard-pipeline、source-capture、ocr、encryption、retention、pet、memory；
- 注册 IPC；
- Event Bus 订阅/转发。

### 3.2 关键服务

| 服务 | 实现要点 | 对 v1.5 的意义 |
|---|---|---|
| `clipboard-pipeline` | 1s 轮询 → normalize → 去重 → 队列 → 串行 worker；检测点取 source snapshot；PNG 编码/落盘在 worker | 主链路必须保持不变；实体识别只能挂在落库之后 |
| `source-capture` | 常驻 PowerShell service，行协议查询前台窗口，故障自动重启 | 提供 sourceApp 上下文；v1.5 不改 |
| `capture-policy` | ignore/metadataOnly 应用列表 + sensitivity 0/1/2；落库前决策 | 是隐私门禁：被忽略/仅元数据/高敏感内容根本不会带内容进入后续分析 |
| `db-service` | better-sqlite3 + WAL；items/notes/items_fts；`user_version` 迁移框架（v1）；insert 时加密 + FTS；删除/清理时同步 FTS；启动备份 | 新表/新列必须走同一迁移框架；备份机制自动覆盖新表 |
| `encryption-service` | AES-256-GCM + scrypt；`enc:v1:` 前缀；未解锁时 decrypt 返回 '' | 实体识别必须遵守：锁定/加密态不得分析内容 |
| `ocr-service` | 事件驱动（OCR_JOB→OCR_DONE），python 脚本异步识别图片 | 图片 OCR 文本（如截图里的故障码）可复用为实体输入，但保持异步 |
| `retention` | maxItems/maxDays/maxImageItems，收藏永不删，启动+每日清理 | 新表数据必须纳入同一清理语义（随 item 删除） |
| `memory-store/search/timeline` | 内存索引：分类/标签/频率/重要性；DB_INSERT 时同步 addMemory；启动时 loadFromDB 重建 | 已有“轻量上下文”雏形，但**不持久化**；实体索引应持久化，不能只靠它 |
| `intent-classifier` | 4 类分类 + #/@/URL/扩展名标签 + 重要性评分 | 规则引擎的先例，实体识别可沿用同风格（本地规则、无依赖） |

### 3.3 数据层

```sql
items (
  id, type, content, filePath, thumbPath, ocrText,
  isFavorite, createTime, fileSize, imageWidth, imageHeight,
  sourceApp, sourceProcess, capturedAt, sensitivity, metadataOnly
)
notes (id, title, content, color, isPinned, createTime, updateTime, remindAt, reminded)
items_fts (fts5 trigram: content, ocrText)
PRAGMA user_version = 1
```

- 搜索：无加密时走 FTS5（英文 trigram）；中文回退 LIKE；加密态内存过滤。
- 删除/清理：`db.remove` / `clearNonFavorites` / `cleanByPolicy` 显式同步 FTS。
- 备份：启动时复制 `shelf.db` + `config.json` 到 `backups/`，保留 5 份。

### 3.4 事件总线

同步 emit，分 SYSTEM/DOMAIN/UI 三层。与 v1.5 相关的现有事件：

- `DB_INSERT`（新记录，含完整 item）
- `DB_DELETE` / `DB_BATCH_DELETE` / `DB_FAVORITE`
- `OCR_JOB` / `OCR_DONE`
- `MEMORY_NEW` / `MEMORY_REPEAT`

实体识别应新增 DOMAIN 事件（如 `ENTITY_JOB` / `ENTITY_DONE`），沿用现有模式。

### 3.5 Renderer / IPC / preload

- App.jsx 单组件状态：`getAll({limit:5000})` 全量加载、客户端过滤；`onUpdate` 增量插入（存在既有 `slice(0,200)` 收敛问题——只记录，不在 v1.5 修）。
- IPC 分组：items / settings(capture/retention/paste/hotkeys) / encryption / notes / memory / ai / ocr / tasks / config 导入导出。
- AI：`ipc-handlers.js` 内 `aiChat()`（DeepSeek 兼容接口，electron net），用于翻译/总结/解释/工单；**不是独立服务，无持久化**。
- Toast：App 内 `showToast`（1.8s）——v1.5 联想提示可复用的基础组件，但需要扩展（带动作/可忽略）。
- 命令面板：已有“打开维修资料文件夹”动作（`FALLBACK_DIRS` 硬编码 `D:\空调资料` 等）——v1.5 资料目录配置应替代/接管这些路径。

### 3.6 测试体系

76 个 node:test（capture-policy / pipeline / db / encryption / markdown / migration / paste-utils / retention / source-capture（含真实 PowerShell）/ pet-tasks）。纯模块可测、主进程依赖通过注入/事件订阅测试。v1.5 新模块沿用此模式。

## 4. 现有架构四问

### 4.1 哪些可以直接复用？

1. **主链路与门禁**：pipeline + capture-policy + sensitivity/metadataOnly——实体识别完全复用其结果，不加第二道判断。
2. **落库/迁移/备份**：db-service 的 `user_version` 迁移框架、WAL、启动备份（新表自动进入备份）。
3. **事件总线**：新增 `ENTITY_JOB/DONE`、`KNOWLEDGE_*` DOMAIN 事件，模式与 OCR 完全一致。
4. **异步执行模式**：OCR 的“事件触发 + 独立子进程/队列”是实体识别和文档扫描的模板；pipeline worker 的队列可参考（不直接复用，见 4.2）。
5. **sourceApp**：联想上下文可直接带来源应用（例如“来自 ima.copilot”），无需新采集。
6. **UI 基础件**：Toast、SettingsPanel 分组、CommandPalette、shell.openPath（`system:openPath` 已存在）。
7. **清理语义**：retention 的“收藏永不删/非收藏按策略清理”应扩展到 entity 数据。
8. **规则引擎风格**：intent-classifier 的本地规则风格（无依赖、可单测）是实体识别的先例。

### 4.2 哪些必须扩展？

1. **db-service**：新增迁移 v2/v3（entities / knowledge 表）；`remove/clearNonFavorites/cleanByPolicy` 需要同步清理实体行（或启用外键级联并评估风险）。
2. **pipeline 之后**：新增独立的异步实体识别服务（订阅 `DB_INSERT` 或新 `ENTITY_JOB`），不在 pipeline worker 内做。
3. **settings**：新增资料目录与联想开关配置（config.json 已有模式）。
4. **IPC/preload**：实体查询、资料扫描/状态/打开、联想配置。
5. **renderer**：联想 Toast（带动作）、设置页新分组；列表/搜索暂不改。
6. **AI 层（v1.6 再议）**：目前 `aiChat` 在 ipc-handlers 内部，v1.5 不引入 AI。

### 4.3 哪些不应该动？

- source-capture（常驻 service，稳定）
- capture-policy 业务规则（sensitivity/ignore/metadataOnly 判定逻辑）
- encryption 核心（密钥派生、加解密、锁定态）
- FTS5 与现有搜索路径
- 备份机制
- 快捷键 / 托盘 / 宠物 / 便签 / 钉图 / 自动更新
- 现有 UI 列表交互（数字粘贴、右键菜单等）
- `slice(0,200)`（只记录，不修）

### 4.4 新能力应该放在哪一层？

建议的分层（结合代码实际）：

```text
Capture Layer        → clipboard-pipeline（不变）
Normalization        → 现有 normalize（不变）
Entity Recognition   → 新 services/entity-recognition.js（异步，订阅 DB_INSERT 后）
SQLite               → db-service 迁移 v2/v3（新表）
Context / Matching   → 新 services/context-matcher.js（异步，消费 ENTITY_DONE）
Local Knowledge      → 新 services/knowledge-index.js（后台扫描/匹配）
Quick Actions / AI   → 复用 shell.openPath / 现有 ai:process（v1.5 不调用 AI）
```

关键点：**实体识别与联想都不得进入 clipboard-pipeline worker**；它们只在“落库完成”之后以事件方式异步执行，这样主链路完全不受影响。

## 5. Entity Recognition 设计（P0-1）

### 5.1 原则

- 本地规则，零第三方依赖（与 source-capture/OCR 一致）；
- 只在 `sensitivity=0 && metadataOnly=0 && content 非空` 的记录上运行；
- 异步，绝不进入复制主链路；
- 第一阶段优先 HVAC 场景，通用实体类型低优先级。

### 5.2 实体类型（v1.5.0）

| 类型 | 示例 | 持久化 | 优先级 |
|---|---|---|---|
| `brand` 品牌 | 大金 / Daikin / 格力 / 美的 / 海尔 / 日立 / 三菱 / 松下 / 富士通将军 | ✅ | 高 |
| `model` 空调型号 | RXYQ16AYM、MDV-xxx、GMV-xxx、KFR-xx | ✅ | 高 |
| `fault_code` 故障代码 | U4、E0–E9、F0–F9、H0–H9、A0–A9、P0–P9、L0–L9 | ✅ | 高 |
| `work_order` 工单号 | 可配置模式（默认 `WO-\d+` 等） | ✅ | 中 |
| `url` | `https://...` | ✅（可选） | 中 |
| `phone` 手机号 | 1[3-9]\d{9} | ⚠️ 默认不持久化 | 低 |
| `email` | 常规邮箱 | ⚠️ 默认不持久化 | 低 |
| `ip` / `mac` / `address` | IPv4 / MAC / 地址 | ❌ v1.5 不做持久化 | 低 |

**明确建议**：`ip / mac / address` 在 v1.5 不实现；`phone / email` 只做内存识别（供统计/调试），默认不落库，避免把个人数据复制进实体表。

### 5.3 HVAC 结构化示例

输入：`大金 RXYQ16AYM U4`

```text
brand  = 大金            （品牌词典命中）
model  = RXYQ16AYM       （品牌锚定型号正则：RXYQ\d+[A-Z]+）
fault  = U4              （故障码正则 + 品牌上下文加权）
```

### 5.4 规则引擎

- **品牌词典**：内置 JSON（`brands.json` 或代码常量）：中文名 + 英文名 + 别名（Daikin/大金金制/格力/GREE 等）。可被用户扩展（后续）。
- **型号规则**：按品牌分组正则（大金 `RXYQ\d+[A-Z]*`、`FTX\d+`；格力 `GMV\d+`；美的 `MDV\d+` 等），外加“通用型号”兜底（字母+数字组合，长度 ≥ 5，避免 U4 这类短码被当型号）。
- **故障码规则**：`[A-Z]\d{1,2}` 但要求：字母在预置集合（U/E/F/H/A/P/L 等）且长度 2–3；**单独出现时不提取**，需品牌/型号上下文或词典命中（如 “U4 故障”），否则误报率高。
- **工单号**：默认 `(WO|WO-|GD|工单)[-：]?\d{4,}`，配置可改。
- **边界控制**：词边界、大小写归一化、禁止从长数字串/版本号/代码串中提取 IP/电话（负向断言 + 前后字符检查）。
- **置信度**：三档：
  - `high`：品牌词典精确命中 / 品牌+型号组合 / 故障码带品牌上下文；
  - `medium`：独立型号正则 / 独立故障码带“故障”词；
  - `low`：模糊命中（默认不参与联想、不持久化，仅调试）。

### 5.5 误识别控制

- 短码（U4/E0）必须满足上下文约束；
- 型号必须有最小长度与结构约束，避免把普通文本当型号；
- 通用词黑名单（如 `OK`、`AI`、`IP` 等）；
- 每个实体记录 `confidence` 与 `match_type`（dict/regex/context），便于调优与单测；
- 规则全部可单测，用真实语料回归（维修手册片段、聊天记录、错误码表）。

### 5.6 性能

- 纯正则 + 词典查表，≤2KB 文本 P95 目标 < 20ms（实测通常 < 5ms）；
- 超过 10KB 的文本只分析前 10KB（记录截断标记），或整体跳过并记录 `entityState=skipped_large`；
- 运行在异步队列（`setImmediate`/微任务链或小 worker），与 pipeline 完全解耦。

### 5.7 与 items 的关系

- `entities.item_id` 指向 items.id；
- 删除 item 时同步删除其实体行；
- 联想/匹配通过实体值反查 items（最近出现时间、收藏、来源）与 knowledge_docs。

## 6. Local Document Index 设计（P1）

### 6.1 第一阶段边界（明确）

- **只索引文件元数据**：路径、文件名、扩展名、大小、修改时间；
- **不读取 PDF/Word/图片内容**（隐私 + 成本）；
- **不做 fs.watch**（增量靠“重扫对比”，watcher 列为后续）；
- 不建向量、不做 embedding。

### 6.2 目录来源

- 设置页配置资料根目录（多选），默认建议 `D:\空调资料`、`D:\空调维修资料`、`E:\空调资料`（与命令面板 FALLBACK_DIRS 对齐，之后由配置接管）；
- 扫描仅限用户显式配置的目录，绝不扫描全盘。

### 6.3 文件名实体提取

复用 5.4 规则引擎（同一实体解析器，输入为文件名）：

```text
大金/RXYQ系列维修手册.pdf   → brand=大金, model_family=RXYQ
U4故障处理.pdf             → fault=U4
VRV故障代码.pdf            → keyword=VRV（通用词，低置信度）
```

文件名提取产出 `knowledge_doc_entities(kind, value, confidence)`。

### 6.4 增量扫描

- `knowledge_docs` 记录 `(path, size, mtimeMs)`；
- 扫描对比：新增 → insert；`size/mtime` 变化 → 重提取并更新；消失 → 删除索引行（含 doc_entities）；
- 触发时机：应用启动后延迟扫描、设置目录变更时、手动“立即扫描”、可选每 6h 一次；
- 大目录扫描放在后台（分批 + `setImmediate` 让步），不阻塞 UI/复制。

### 6.5 数据库规模与权限

- 普通维修资料目录（几百到几千文件）完全无压力；
- 权限/长路径/UNC：不可读目录跳过并计入状态（`lastScanErrors`）；扫描结果在设置页展示；
- 文件被移动/删除：下次扫描移除索引（第一阶段不保留墓碑）。

### 6.6 与 Entity Recognition 的连接

- 两边产出相同结构的 `(kind, value, confidence)`；
- 匹配时统一打分（见第 7 节）；
- 同一规则引擎保证“复制文本提取的型号”与“文件名提取的型号”格式一致。

## 7. Copy-to-Context Matching 设计（P0-2）

### 7.1 流程

```text
新记录落库
  → ENTITY_JOB（异步实体识别）
  → ENTITY_DONE（entities 已写库）
  → context-matcher 触发（带冷却/防骚扰）
  → SQLite 查询 knowledge_doc_entities
  → 打分 → 超过阈值 → renderer Toast
```

### 7.2 打分与阈值

```text
score = w(fault)*命中 + w(model)*命中 + w(brand)*命中 + 文件名直接包含加权
w(fault) > w(model) > w(brand)
```

示例：

- `大金 U4` + 文件 `U4故障处理.pdf`（fault 命中）→ 高置信；
- `大金 U4` + 文件 `大金维修手册.pdf`（仅 brand 命中）→ 不提示（单品牌命中太弱）；
- 无任何实体命中 → 不提示。

建议默认阈值：至少一个 `high` 或两个 `medium` 命中；具体数值用真实语料标定后写入配置。

### 7.3 防骚扰机制（核心）

- **默认关闭**（联想 Toast 默认 off，设置里开启）；主列表/面板内“相关”入口不受此限制；
- **cooldown**：同一实体签名（brand+model+fault 组合）N 分钟内不重复提示（默认 30–60min）；
- **全局 debounce**：两次提示间隔至少 60s；
- **忽略记忆**：用户点击“忽略”后，该实体签名 24h 内不再提示；
- **低置信内容不提示**：普通文本/代码/URL 不触发（实体为空的直接短路）；
- **图片来源**：OCR 文本可参与，但仅当识别到 HVAC 实体；
- 原则：宁可少提示，也不能骚扰。

### 7.4 UI 位置

1. **轻 Toast（主推）**：`🔧 找到 3 份相关资料`，点击打开文件列表（或直接打开 top1，设置可选）；可“忽略”；
2. **命令面板条目（次推）**：`查看相关资料`，展示当前上下文命中的文件；
3. 后续可考虑 ItemRow 上下文菜单“查看相关资料”（v1.5.2 若有余量）。

## 8. 数据库设计（最小化）

原则：**能复用现有表就不新建表**；不为“未来可能”提前建表。

### 8.1 结论

| 表 | 是否新建 | 理由 |
|---|---|---|
| `entities` | ✅ 新建（v1.5.0，migration v2） | 实体需要按 (type, normalized) 索引、跨 item 聚合；塞进 items 的 JSON 列无法高效查询 |
| `entity_occurrences` | ❌ 不新建 | `entities` 本身就是 occurrence（带 item_id），不需要第二张表 |
| 独立 `entity_dictionary` 表 | ❌ 不新建 | 品牌/型号/故障码词典先用代码/JSON 内置，规则可单测；词典可编辑是 v1.6+ |
| `item ↔ entity` 关系表 | ❌ 不新建 | `entities.item_id` 直接表达关系 |
| `knowledge_docs` | ✅ 新建（v1.5.1，migration v3） | 文档索引生命周期与 items 无关 |
| `knowledge_doc_entities` | ✅ 新建（v1.5.1，migration v3） | 匹配需要按 (kind, value) 反查文档 |
| 扩展 `items` | ⚠️ 只加一列 `entityState` | 标记识别状态（0 未处理 / 1 完成 / 2 跳过），避免重复识别队列 |

### 8.2 v1.5.0 迁移（v2）

```sql
ALTER TABLE items ADD COLUMN entityState INTEGER DEFAULT 0;

CREATE TABLE entities (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  item_id INTEGER NOT NULL,
  type TEXT NOT NULL,          -- brand / model / fault_code / work_order / url
  value TEXT NOT NULL,         -- 原始归一化值（小写/去空格）
  confidence INTEGER NOT NULL, -- 0-100
  match_type TEXT NOT NULL,    -- dict / regex / context
  createTime INTEGER NOT NULL
);
CREATE INDEX idx_entities_item ON entities(item_id);
CREATE INDEX idx_entities_type_value ON entities(type, value);
```

删除语义：`db.remove` / `clearNonFavorites` / `cleanByPolicy` 中，对被删 item ids 同步 `DELETE FROM entities WHERE item_id IN (...)`。

### 8.3 v1.5.1 迁移（v3）

```sql
CREATE TABLE knowledge_docs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  path TEXT NOT NULL UNIQUE,
  filename TEXT NOT NULL,
  ext TEXT NOT NULL,
  size INTEGER NOT NULL,
  mtimeMs INTEGER NOT NULL,
  indexedAt INTEGER NOT NULL
);

CREATE TABLE knowledge_doc_entities (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  doc_id INTEGER NOT NULL,
  kind TEXT NOT NULL,          -- brand / model / fault_code / keyword
  value TEXT NOT NULL,
  confidence INTEGER NOT NULL
);
CREATE INDEX idx_kdoc_entities_kind_value ON knowledge_doc_entities(kind, value);
CREATE INDEX idx_kdoc_entities_doc ON knowledge_doc_entities(doc_id);
```

### 8.4 不做的东西

- 不建 `knowledge_sources` 目录表（目录配置放 config.json）；
- 不建向量/embedding 表；
- 不给 entities 建 FTS（规范化值 + LIKE/索引足够）。

## 9. IPC / API 设计

### 9.1 主进程 → Renderer 新增

```text
context:suggestion        事件推送：{ entitySignature, docs:[{path,name,score}], total }
knowledge:statusChanged   事件推送：扫描状态变化（可选）
```

### 9.2 Renderer → 主进程新增（preload 包装）

```text
entities:getByItem(itemId)                    → 某条记录识别出的实体
entities:search({type, value, limit})         → 按实体查历史（调试/后续搜索增强）
knowledge:getStatus()                         → { dirs, totalDocs, lastScanAt, errors }
knowledge:scan()                              → 触发后台扫描
knowledge:setDirs(dirs)                       → 更新资料目录并触发扫描
knowledge:openFile(path)                      → 复用 shell.openPath 语义
knowledge:getMatches({type, value})           → 内部/调试
context:getLastSuggestion()                   → 当前上下文联想结果
settings:getContextOptions() / setContextOptions({enabled, cooldownMin, threshold})
settings:getEntityTypes() / setEntityTypes()  → 持久化实体类型开关（默认 brand/model/fault）
```

### 9.3 约束

- 所有新增 IPC 遵循现有 preload 白名单模式；
- `knowledge:openFile` 只接受已索引路径（防任意文件打开）；
- 联想结果不携带文件内容。

## 11. 性能设计

### 11.1 硬约束

> 任何复制操作都不能因为 v1.5 明显变慢；实体识别/联想不得阻塞剪贴板主链路。

### 11.2 时序设计

```text
复制 → poll 检测（≤1s，不变）
     → 落库（不变）
     → ENTITY_JOB（异步，识别 ≤20ms 目标）
     → entities 写入（单事务，≤5ms）
     → context matcher（异步，SQLite 查询 ≤10ms）
     → Toast（仅高置信 + 开关开启）
```

### 11.3 具体措施

- 实体识别与匹配都在独立异步队列，绝不进 pipeline worker；
- 大文本截断（>10KB 只分析前 10KB）；
- entities 写入与主 insert 分离（主 insert 不加任何新逻辑）；
- 文档扫描分批（每批 50 文件后 `setImmediate` 让步），后台执行；
- 联想查询加索引（type+value）与 LIMIT；
- 性能验收指标（本机）：
  - 实体识别 P95 < 20ms（≤2KB）；
  - 实体写入对主链路零增量（异步）；
  - 联想查询 P95 < 10ms；
  - 全库 10 万实体时无可见退化。

## 12. 隐私与安全

继承 v1.4.1 原则，新增能力必须遵守：

1. **敏感门禁**：实体识别只运行于 `sensitivity=0 && metadataOnly=0 && content 非空`；
2. **忽略应用**：capture policy 已拦截，实体层不再见到这些内容；
3. **仅元数据应用**：content 为 null，实体层无内容可分析；
4. **加密态**：加密启用且锁定时不得分析（insert 时解密为空）；建议实体识别仅在“加密未启用或已解锁”时运行；
5. **实体持久化白名单**：默认只持久化 brand/model/fault/work_order/url；phone/email 仅内存识别，不落库；ip/mac/address 不实现；
6. **文档索引**：只读元数据，绝不读取 PDF/Word/图片正文；
7. **不上传**：实体表、文档索引全部本地；AI 调用（v1.6）也必须显式用户触发；
8. **不新增窗口标题采集**；
9. **打开文件**：仅允许打开已索引路径。

## 13. 测试策略

### 13.1 单元测试（node:test，沿用现有体系）

- **entity rules**：HVAC 正向用例（`大金 RXYQ16AYM U4` → 3 实体）；误报用例（纯 U4、版本号 `v1.4.1`、代码片段、长数字串、URL 内 IP）；
- **entity persistence**：migration v2 建表、insert/delete/清理联动；
- **knowledge scan**：临时目录构造文件集，验证增量扫描/变化/删除/权限错误；
- **context matcher**：打分、阈值、cooldown、忽略名单；
- **异步不阻塞**：模拟 DB_INSERT 后识别在事件循环外完成，pipeline 测试不变绿即回归；
- **privacy gate**：sensitivity=1/2、metadataOnly、ignore app 场景下 ENTITY_JOB 不产生。

### 13.2 回归

- 现有 76 测试保持全绿；
- pipeline/source-capture/retention/encryption 测试不得修改行为断言（除必要的清理联动）；
- 迁移测试新增 v0 → v2 → v3 路径与旧数据保留验证。

### 13.3 实机验收

- 复制故障文本 → 观察实体与提示；
- 连续复制/大文本复制 → 无卡顿；
- 加密启用后锁定 → 无实体产生；
- 资料目录增删文件 → 扫描正确；
- 高频复制 2 分钟 → 联想不骚扰。

## 14. 版本拆分建议

### 推荐顺序（按依赖与风险）

**v1.5.0 —— 本地实体识别**

- migration v2（entities + items.entityState）；
- entity-recognition 服务 + 规则引擎 + 品牌/型号/故障码词典；
- 隐私门禁与清理联动；
- 设置页实体类型开关；
- 单测 + 实机验收。

**v1.5.1 —— 本地资料索引**

- migration v3（knowledge_docs + knowledge_doc_entities）；
- knowledge-index 服务（元数据扫描、增量、文件名实体提取）；
- 设置页目录配置 + 手动扫描 + 状态；
- IPC 打开文件。

**v1.5.2 —— 复制即联想**

- context-matcher（打分/阈值/cooldown/忽略）；
- 联想 Toast（默认关闭）+ 命令面板入口；
- 联想设置（开关/冷却/阈值）。

### 备选顺序

- 若希望尽早看到产品价值，可先做 v1.5.1（资料索引独立、无需实体），再 v1.5.0/1.5.2；
- 但文件名实体提取会复用 v1.5.0 规则引擎，因此“实体先行”开发成本更低，维持推荐顺序。

### 明确排除出 v1.5

- PDF/Word 正文内容提取与检索（v1.6 候选，需先解决隐私与成本）；
- AI 摘要/问答（v1.6 候选）；
- fs.watch 实时监听（可后补）；
- 词典/规则的用户自定义编辑器（v1.6+）。

## 15. 风险清单

| 风险 | 等级 | 缓解 |
|---|---|---|
| 实体误识别导致骚扰 | 高 | 默认关闭联想；阈值/冷却/忽略；规则单测 + 真实语料标定 |
| 实体表随历史增长 | 中 | 随 item 清理；retention 联动；上限告警 |

| 加密/锁定态误分析 | 高 | 隐私门禁 + 测试覆盖 |
| 迁移破坏生产库 | 高 | 沿用 user_version 框架 + 启动备份；迁移测试 v0→v2→v3 |

| 新 IPC 扩大攻击面 | 低 | 白名单 preload；openFile 仅限已索引路径 |
| 开发工作量被高估/低估 | 中 | 三版本各自独立可交付，任一层可单独发布 |

## 17. 结论

v1.5 的核心不是“更多功能”，而是：

> **在复制主链路零影响的前提下，用本地规则把“复制内容”变成“可匹配的上下文”，并只在高置信时给出极轻的本地资料联想。**

推荐按 **v1.5.0（实体识别）→ v1.5.1（资料索引）→ v1.5.2（复制即联想）** 拆分，每版独立可交付、独立验收；AI/正文检索/实时监听明确留到 v1.6 再评估。
