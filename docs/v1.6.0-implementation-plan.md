# Clipboard Shelf v1.6.0 实施设计

> 状态：Design / 实施前规划（零代码修改）
> 基线：v1.5.0（已发布、已冻结、Git clean）
> 核心目标：**把 v1.5.0 已经识别出来的实体真正变成用户能看见、能搜索、能过滤、能回溯的能力。**

---

## 1. 产品目标

一行目标：

> 让实体资产“通电”：**看得见 → 搜得到 → 点得动 → 能回看**。

不做：AI、文档扫描、云同步、知识库、新表、新依赖。

第一优先级功能：

1. 实体可见化（列表 Badge / Chip）
2. 实体搜索（裸词命中实体关联记录）
3. 类型过滤（`品牌:` / `型号:` / `故障:` / `制冷剂:`）
4. 点击实体直接过滤
5. 型号历史（轻量回溯视图）

---

## 2. 当前架构盘点（只读审计结论）

### 2.1 数据流

```text
复制 → pipeline（冻结）→ db.insert → entities（v1.5.0 异步写入）
UI：App.loadItems → window.api.getAll → ipc items:getAll → db.getAll → ItemList(Virtuoso) → ItemRow
搜索：SearchBar(search state) → debounce 250ms → loadItems(search, filter) → getAll({search, limit:5000})
```

### 2.2 关键事实

| 项 | 现状 | 对 v1.6 的意义 |
|---|---|---|
| UI 列表渲染 | `ItemList.jsx`（Virtuoso 虚拟滚动）+ `ItemRow.jsx` | Badge 加在 ItemRow 的 meta 行最合适 |
| 搜索入口 | `SearchBar.jsx` 受控输入，App 持有 `search` state | 实体语法直接复用同一输入框 |
| 搜索逻辑 | `db-service.getAll`：FTS5/LIKE + 加密内存过滤；`ORDER BY isFavorite DESC, createTime DESC` | 实体匹配作为**附加条件**并入现有查询，不新建搜索引擎 |
| 多选状态 | App `selectedIds` + `multiMode`，ItemList 透传 | 与 v1.6 无冲突，不需要改 |
| IPC/preload | `items:getAll` 直接把 opts 透传给 `db.getAll(opts)` | **增加 opts 字段即可，IPC/preload 零改动** |
| entities 查询能力 | 仅有 `getEntitiesByItem(itemId)`；索引 `(item_id)`、`(type,value)` | 需新增按实体反查 item 的查询（纯 SQL，不建表） |
| 分页/排序 | 无分页；renderer 一次取 5000，Virtuoso 虚拟化；排序固定 | 需新增可选 `sort:'time'` 用于“型号历史”严格时间倒序 |
| `slice(0,200)` | 只在 `onUpdate` 增量插入路径截断（App.jsx:142） | 见第 5 节专项分析 |
| 实体规则 | 品牌词典/型号正则/归一化都在 `entity-recognition.js` 内部 | 查询端归一化需与识别端一致 → 抽共享规则模块 |

### 2.3 复用结论

- 直接复用：`entities` 表 + 索引、现有搜索框、现有 getAll 管道、Virtuoso、现有 IPC/preload 透传。
- 必须小改：`db-service.getAll`（可选新参数）、`ItemRow/ItemList/App`（展示与点击）、新增共享规则模块与查询解析模块。
- 不需要动：pipeline、capture-policy、sensitivity、encryption、retention、FTS5 结构、图片链路、快捷键、托盘、自动更新。

## 3. UI 改造点

### 3.1 ItemRow：实体 Chip

- 在 meta 行（时间/来源/敏感徽标旁）追加紧凑 Chip，最多显示 4 个，顺序固定：
  `品牌 → 型号 → 故障码 → 制冷剂`（URL 不显示，避免噪音）。
- Chip 样式：小号圆角标签（与现有 OCR/敏感徽标风格一致），可点击，可 hover 提示“过滤：品牌:大金”。
- 点击行为：
  - `大金` → 搜索框设为 `品牌:大金`
  - `RXYQ16AYM` → 搜索框设为 `型号:RXYQ16AYM`（即“型号历史”入口）
  - `U4` → `故障:U4`；`R410A` → `制冷剂:R410A`
- 数据来源：`getAll({withEntities:true})` 返回每行 `entities` 数组（见第 10 节）。

### 3.2 SearchBar：语法提示与激活态

- placeholder 更新为：`搜索剪贴板… 支持 品牌:大金 / 型号:RXYQ16AYM / 故障:U4 / 制冷剂:R410A`
- 输入框下方（或框内）展示已解析出的实体过滤条件 Chip，可单独删除；普通关键词仍走原搜索。
- 不做单独“高级搜索”面板。

### 3.3 型号历史视图

- 点击型号 Chip 后，主列表即变为“该型号全部历史”（`型号:RXYQ16AYM` + `sort=time`），时间倒序；
- 顶部可显示当前过滤语义（复用搜索 Chip）；
- 不新增页面/路由/抽屉，保持轻量。

## 4. 搜索架构

### 4.1 解析层（新增纯模块，可在 renderer 使用）

新增 `src/shared/entity-query.cjs`（无依赖，浏览器/Node 通用）：

```text
输入：'品牌:大金 故障:U4 R410A'
输出：
{
  plain: ['R410A'],                      // 普通关键词（不进入实体匹配，走原内容/OCR/FTS）
  entityFilters: [
    { type: 'brand', value: '大金' },
    { type: 'fault_code', value: 'U4' }
  ]
}
```

规则：

- 支持中英文类型前缀：`品牌:` / `型号:` / `故障:` / `制冷剂:`（及 `brand:` / `model:` / `fault:` / `refrigerant:`）；
- 未知前缀（如 `颜色:红`）→ 整段按普通关键词处理，不报错；
- 前缀后为空 → 忽略该 token；
- 多 token 默认 **AND**（普通关键词之间维持现有搜索语义，实体过滤之间 AND，两类之间 AND）；
- 归一化由共享规则模块完成（见 4.2），保证 `型号:GMV450W` 能命中存储值 `GMV450W`。

### 4.2 共享规则模块（新增）

把识别端规则抽到 `src/shared/entity-rules.cjs`：

- `BRANDS`（含别名）、`REFRIGERANTS`、`FAULT_LETTERS`
- `normalizeModel(raw)`（大写、去 `- / 空格`）
- `normalizeQuery(type, value)`：
  - `brand`：先查别名反解（`daikin → 大金`），再原样；找不到别名则原样（后端用 `value = ?` 精确匹配）
  - `model`：`normalizeModel`
  - `fault_code` / `refrigerant`：大写
- `entity-recognition.js` 改为引用该模块（行为不变，v1.5.0 测试必须保持全绿）。

### 4.3 匹配语义

- 类型过滤 = **精确匹配归一化值**（`entities.type = ? AND entities.value = ?`）；
- 型号额外支持前缀模式（`value LIKE 'RXYQ%'`）作为候选，v1.6 默认只做精确，是否开放前缀由你决定（见第 9 节待确认项）；
- 普通关键词沿用现有内容/OCR/FTS 匹配，不再做实体 OR 命中（避免结果膨胀）；
- 多条件 = 各实体过滤的 item_id 集合取交集，再与普通关键词结果取交集。

## 5. `slice(0,200)` 专项评估

### 5.1 影响路径

- 仅影响 `App.jsx` `onUpdate` 的**增量插入**分支（`[item, ...prev].slice(0,200)`）；
- 不影响：初次加载（limit 5000）、搜索/过滤重新加载、收藏切换、删除。

### 5.2 是否阻碍 v1.6

**不阻碍。**

- 实体 Chip 展示依赖 `getAll` 返回的行与 entities——初次加载与过滤加载都全量可达；
- 实体搜索/型号历史走的是“重新 getAll”，不是增量列表；
- 唯一副作用：长时间使用后可见列表收敛到 200 条（既有观感问题），与 v1.6 无关。

### 5.3 是否必须一并解决

**不必需。** 如果希望一并解决，最小方案是：

```js
// App.jsx onUpdate 增量分支
const next = [item, ...prev]   // 去掉 slice(0,200)，Virtuoso 本身支持大数据量
```

一行改动、无副作用（初始即 5000 行全量数组）。**是否纳入 v1.6.0 由你决定。**

## 6. Entity 查询 API

### 6.1 新增 db-service 能力（不改表）

```text
getAll({
  search, limit, type, favorite,          // 现有
  entityFilters: [{ type, value }],        // 新增：AND 语义
  withEntities: boolean,                   // 新增：返回行附带 entities 数组
  sort: 'default' | 'time'                 // 新增：型号历史用 time
})
```

### 6.2 内部实现

- 实体过滤：对每个 filter 执行
  `SELECT item_id FROM entities WHERE type = ? AND value = ?`，
  取交集得到 `idSet`；
- 与现有查询组合：在原有 SQL 的 WHERE 上追加 `AND id IN (...)`
  （与 type/favorite/search 全部 AND）；
- 实体过滤为空集 → 直接返回 `[]`（不扫 items）；
- `withEntities`：对返回行执行
  `SELECT item_id, type, value, confidence FROM entities WHERE item_id IN (...)`，
  **按 500 个 id 分块**（避免超长 IN），按行组装为 `item.entities`；
- `sort:'time'`：`ORDER BY createTime DESC`（型号历史），默认保持现有排序不变。

### 6.3 归一化发生在哪

- renderer 解析时已用共享规则归一化（展示/回填）；
- db-service 侧做**防御性归一化**（同一共享模块），保证 IPC 直调也正确。

## 7. IPC / preload 改造

- `ipc-handlers.js`：**零改动**（`items:getAll` 已透传 opts）；
- `preload/index.js`：**零改动**（`getAll: (opts) => ipcRenderer.invoke('items:getAll', opts)` 已透传）；
- 新增 IPC：**不需要**（型号历史 = `getAll({entityFilters:[{type:'model',value}], sort:'time'})`）。

## 8. 型号历史页面/面板设计

- 形态：**过滤态主列表**，不是新页面；
- 触发：点击型号 Chip 或输入 `型号:RXYQ16AYM`；
- 数据：`getAll({ entityFilters:[{type:'model',value:'RXYQ16AYM'}], limit:5000, sort:'time', withEntities:true })`；
- 展示：主列表 + 搜索框内实体 Chip；支持继续叠加条件（如再加 `故障:U4`）；
- 退出：清空搜索/删除 Chip，回到普通列表。

## 9. 过滤语法设计

```text
品牌:大金 故障:U4          → AND，仅同时含两实体的记录
型号:GMV450W              → 归一化后精确匹配
制冷剂:R410A 泄漏          → 实体过滤 AND 普通关键词“泄漏”
RXYQ16AYM                → 普通搜索（内容命中，行为不变）
品牌:daikin               → 别名反解为 大金
颜色:红                   → 未知前缀，按普通关键词
```

大小写：型号/故障/制冷剂不区分大小写（归一化）；品牌按词典别名反解。

待确认项：

1. 型号是否支持前缀匹配（`型号:RXYQ` → 所有 RXYQ 系列）？默认建议**仅精确**，前缀留后续。
2. 未知前缀按普通关键词（建议）还是显示提示？
3. 品牌别名反解是否覆盖英文别名（建议覆盖，复用词典）。

## 10. 数据库查询方案

```sql
-- 实体过滤（每个 filter 一次，命中索引）
SELECT item_id FROM entities WHERE type = ? AND value = ?;

-- withEntities（对返回行按块）
SELECT item_id, type, value, confidence
FROM entities
WHERE item_id IN (?, ?, ...)   -- 每块 ≤500

-- 型号历史
SELECT * FROM items
WHERE id IN (SELECT item_id FROM entities WHERE type='model' AND value=?)
ORDER BY createTime DESC
LIMIT ?;
```

无新表、无 entity FTS、无字典表、无 embedding。

## 11. 性能分析

- 实体过滤：`(type,value)` 索引命中，单条件 <2ms；
- withEntities：一次分块查询，5000 行约 3–8ms；
- 普通关键词：维持现有 FTS/LIKE 路径，无新增开销；
- 型号历史：走索引 + `ORDER BY createTime DESC`（已有 `idx_items_time`），5000 行内 <10ms；
- 验收指标：实体过滤/型号历史查询 **P95 < 20ms**；列表加载不增加可感知延迟。

---

## 12. 隐私影响

- Chip 展示的是用户自己剪贴板内容的实体（本来就在 content 里可见），无新增数据暴露；
- 敏感/仅元数据记录不产生实体（v1.5.0 门禁），因此 Chip 天然不会出现在敏感记录上；
- URL 默认不展示，避免噪音；
- 无新采集、无上传、无扫描。

---

## 13. 错误处理

- 语法解析失败/未知前缀：降级为普通关键词，不弹错误；
- 空值过滤：忽略；
- 数据库异常：沿用现有 try/catch 回退（FTS 失败回 LIKE）；
- 空结果：正常空列表（“没有找到内容”），不视为错误；
- withEntities 分块失败：该行 entities 置空数组，不影响列表。

## 结论

v1.6.0 是**消费型版本**：不建任何新后台能力，只把 v1.5.0 的实体资产通过
“Chip 可见 → 裸词可搜 → 点击即过滤 → 型号可回看”接到现有工作流上。
改动集中在共享规则模块、db-service 读取参数与 renderer 展示层，风险低、可独立验收。
