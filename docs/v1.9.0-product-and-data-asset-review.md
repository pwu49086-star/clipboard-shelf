## 0. 结论摘要（10 问速答）

1. **Clipboard Shelf 现在是什么？**
   不再只是“剪贴板管理器”，而是**本地优先的维修现场资料工作台 / 工作上下文入口**：从复制捕获出发，经过实体识别、现场归组、图片工具与输出，收敛为可交付的维修记录。
2. **v1.8 后最重要的数据资产是什么？**
   剪贴板正文（`items.content` / `ocrText`）与**图片本体（full/thumb/annotated）**并列第一；实体、现场、标注是支撑结构，但离开正文与图片就无法重建。
3. **什么才算“完整备份”？**
   `DB（一致快照）+ Config + pet-tasks.json + encryption.json + 全部图片资产（full/thumb/annotated）+ Integrity Manifest（DB 哈希 + 每文件 sha256/size/mtime + 行↔文件映射）`。缺任一项都存在无法完整恢复的场景（详见 §12）。
4. **当前 backup 最大漏洞是什么？**
   图片本体完全不进备份；其次是启动时对主 DB 文件做裸拷贝，WAL 未落盘时可能静默丢失最近事务（详见 §6）。
5. **是否应该做 Asset Integrity？**
   **应该，且应立即做只读诊断版**。生产实测已同时存在 205 条 `MISSING_FILE` 与 9 个 `ORPHAN_FILE`，两个方向的不一致都真实发生。
6. **v1.9 最值得做什么？**
   **Backup & Recovery（完整备份 + 恢复 + 验证）**。这是本次事故唯一未被系统性解决的根因，也是其他一切能力的前提。
7. **Backup / Recovery 是否排第一？**
   是。用户痛点最高、使用频率虽低但后果最重、与现有架构复用高、不需要 AI、不需要新 schema（只加 manifest 文件）。
8. **图文维修报告是否排第二？**
   是（P1）。它复用现有实体/标注/OCR/工单草稿，是“输出闭环”的自然延伸；但与备份相比仍属锦上添花。
9. **AI 应该现在做，还是继续延后？**
   **继续延后**。当前 AI 仅作为图片工具内的可选动作（总结/解释/工单），不进入核心链路；v1.9 不引入“AI Worksite / AI 整理”。
10. **哪些旧 backlog 正式砍掉？**
    Document Index、Context Matching、Toast 联想、云同步、RAG、Embedding 正式砍掉/无限期冻结；型号前缀、Entity 实时推送降为 P2 暂缓。

## 1. 当前产品定位

从 v1.5（实体识别）→ v1.6（实体可见/搜索）→ v1.7（Worksite）→ v1.8（图片工具）的真实演进看，产品主线已经稳定为：

```text
Clipboard Capture
      ↓
History（正文 + 图片 + OCR）
      ↓
Entity Recognition → Entity Search
      ↓
Collection（多选/复制/Markdown）
      ↓
Worksite（现场归组）
      ↓
Image Tools（标注 + 提取/翻译/AI）
      ↓
Output（Markdown 导出 / 工单草稿）
      ↓
维修记录
```

**定位结论：** Clipboard Shelf = **本地优先的维修现场资料工作台 / 工作上下文入口**。

证据：
- v1.7 Worksite 使“一次维修任务”成为一等公民；
- v1.8 图片工具让“现场证据”可标注、可提取、可翻译、可输出；
- Collection & Output 已经能把多段记录整理成维修记录/工单草稿；
- 所有能力全部本地完成，无云依赖。

它不是 CRM / ERP / 工单 SaaS / 网盘 / 知识库平台；也不应变成这些（见 §14）。

| -- | -- | -- |

| Retention / 清理 | 生命周期 | 支撑（本次事故高相关） |

**重叠点：**
- OCR 存在两条路径：捕获时自动 OCR（写入 `ocrText`）与图片工具内手动“提取文字”。两者结果可能不同步，建议后续统一读取 `ocrText` 优先、手动提取兜底。
- 工单草稿存在两处入口：Collection 输出层与图片工具的 AI 生成工单。前者是确定性整理，后者是 AI 生成，语义不同，需在 UI 上明确区分（现状已通过按钮文案区分）。
- 图片预览“查看原图 / 标注图”与图片工具内的再编辑基图是同一套语义，无冲突。

## 3. 用户工作流与闭环判断

1. **是否已形成完整产品闭环？** 基本形成：复制 → 历史 → 实体 → 检索 → 归组 → 图片工具 → 输出 → 维修记录。缺口在**资产的长期可恢复性**（备份/恢复）与**图文合并输出**（带图报告）。
2. **核心能力**：捕获、实体、Worksite、Image Tools、Collection & Output。
3. **辅助能力**：便签、宠物、记忆、皮肤。
4. **互相重叠**：OCR 双路径；工单草稿双入口（确定性 vs AI）；翻译的在线端点（Google/MyMemory/AI）多级回退。
5. **是否失去主线？** 没有。v1.6→v1.8 全部沿“把复制内容变成维修现场资料”的主线推进；真正的风险是功能继续堆叠而资产仍不可恢复。
6. **下一阶段：增加连接，还是增加功能？** **增加连接（尤其“资产↔备份↔恢复”的连接）**，而不是增加新功能。

- 文件资产（full/thumb/annotated）**完全不进备份**，是当前唯一“不可恢复”的资产类别，也是本次事故的直接根源。

## 5. 图片资产生命周期

```text
捕获（clipboard-pipeline.saveImage）
  ├─ 写 images/full/<ts>_<rand>.png
  ├─ 写 images/thumb/<ts>_<rand>.jpg
  └─ enqueue → processItem → DB insert（filePath/thumbPath）
        ↓
异步 OCR → updateOcrText
        ↓
图片工具保存标注（ipc-handlers annotations:save）
  ├─ 写 images/annotated/<itemId>_<ts>.png
  ├─ replaceAnnotations（非 mosaic 行替换，mosaic 行保留）
  ├─ setItemAnnotatedPath
  └─ unlink 旧 annotated（失败被吞）
        ↓
删除/清理（delete/batchDelete/clearNonFavorites/cleanByPolicy/retention）
  └─ 删行 + unlink full/thumb/annotated（失败被吞）
```

**孤儿窗口（代码审查确认）：**
- 捕获：full/thumb 写入成功后、DB insert 前崩溃 → 文件孤儿；
- 标注：annotated 写入成功后、`setItemAnnotatedPath` 前崩溃 → 文件孤儿 + 旧路径残留；
- 删除/清理：`unlink` 全部包在 `try/catch` 且失败静默 → 行已删、文件残留；
- 进程强杀（本阶段多次 `Stop-Process -Force` 场景）会放大上述窗口。

**生产实测（2026-08-14，只读扫描）：**

| 指标 | 数值 |
| -- | -- |
| DB 图片行（filePath 非空） | 207 |
| full 文件存在（行可访问） | **2** |
| full 文件缺失（MISSING_FILE） | **205** |
| thumb 文件存在 | 2 |
| thumb 缺失 | 205 |
| annotatedPath 非空 | 0 |
| 磁盘 full 文件数 | 11 |
| 磁盘 orphan full 文件（无 DB 引用） | **9**（含 7 个历史截图） |
| 磁盘 thumb 文件数 / orphan | 11 / 9 |
| annotated 文件 | 0 |

结论：**生产环境已同时出现“有行无文件”与“有文件无行”两个方向的断裂**。205 条缺失与事故记录一致；9 个孤儿文件是幸存但已不可见的真实资产——它们恰好证明 Asset Integrity 与“图片恢复/重新挂载”工具的价值。

## 6. Backup 现状

实现（`db-service.js backupDatabase()`）：
- 时机：**仅应用启动时、打开 DB 之前**（`init()` 内调用一次），无定时备份、无关闭备份；
- 方式：`fs.copyFileSync(shelf.db, backups/shelf-<ts>.db)` + `copyFileSync(config.json, config-<ts>.json)`；
- 保留：`shelf-*.db` 只保留最近 5 份；**config-*.json 不清理**（生产目录已积累约 90 份）；
- 范围：**不含 images/full、thumb、annotated、pet-tasks.json、encryption.json**。

**WAL 一致性问题（代码审查确认）：**
- DB 为 WAL 模式；干净退出时 SQLite 会在最后连接关闭时 checkpoint，但**崩溃/强杀后 WAL 未落盘**；
- 下次启动先执行备份（裸拷贝主 DB 文件）、再打开 DB 恢复 WAL → **备份会静默丢失最近未 checkpoint 的事务**；
- 生产当前 `shelf.db-wal` 约 4.3 MB（说明存在未落盘数据），若此刻发生启动备份，这部分将不进备份；
- 未使用 SQLite 官方 `backup API`（`sqlite3_backup`），也没有 `PRAGMA wal_checkpoint` 前置。

**现有备份目录实测：** `backups/` 内 `shelf-*.db` ×5（各 23,461,888 B，同日同一份内容，疑似连续启动产生），`config-*.json` 约 90 份，另有历史手工拷贝残留的 `-shm/-wal` sidecar（清理逻辑只按 `shelf-*.db` 匹配，sidecar 永不清理）。

**结论：** 当前“备份”既**不完整**（无图片），也**不保证一致**（WAL），只能视为“启动快照”，不能视为“可恢复的备份”。

## 7. Recovery 问题

现状恢复路径（人工）：
1. 停止应用；
2. 从 `backups/shelf-*.db` 复制回 `shelf.db`，`config-*.json` 复制回 `config.json`；
3. 启动。

问题：
- **图片本体无法恢复**（本次事故：DB 恢复后 205 张图片永久缺失，已接受）；
- **encryption.json 丢失则加密数据不可解锁**；
- pet-tasks 不恢复（影响小）；
- 恢复后**没有任何自动验证**：DB 是否可打开、行↔文件是否一致、FTS 是否可用、retention 配置是否正确，全靠人工；
- 恢复会覆盖当前生产数据，无回滚、无二次确认机制（当前为纯手工，反而“无确认”）。

因此 v1.9 的 Recovery 目标不是“有一个 backup 文件”，而是：

```text
Backup → DB → Config → Images → Annotations → Worksites
  → 验证（DB 可打开 / 行数一致 / 文件齐全 / 实体一致 / 标注一致 / worksite 关联一致
           / annotatedPath 有效 / full-thumb-annotated 可访问 / FTS 可用 / retention 正确）
  → Restore（二次确认，必要时整目录重建）
```

## 8. Asset Integrity

现状：**不存在任何一致性巡检**；删除、迁移、捕获都不校验行↔文件。

需要覆盖的五种情况（均已映射到生产/代码证据）：

| 情况 | 定义 | 生产实测 | 建议处置 |
| -- | -- | -- | -- |
| A MISSING_FILE | DB 有图片行，full 不存在 | **205 条** | 报告 + 可选“标记/重建缩略图” |
| B ORPHAN_FILE | full 存在，DB 无引用 | **9 个** | 报告 + 可选“重新挂载为记录” |
| C MISSING_ANNOTATED | annotation 数据存在，annotated PNG 不存在 | 0（当前无标注） | 报告 + 可从元素 JSON 重新合成 |
| D ORPHAN_ANNOTATED | annotated PNG 存在，无 annotation/无行 | 0 | 报告 + 删除或回收 |
| E CORRUPTED_OR_CHANGED | 文件 hash/size 与记录不符 | 未测（无 manifest 基线） | 报告 |

**建议形态（v1.9）：**
- 默认**只读诊断**，不自动删除/移动任何文件；
- 输出 JSON/文本报告（`MISSING_FILE` / `ORPHAN_FILE` 等清单）；
- 可在设置中手动触发；开机自动运行可作为可选项（默认关），性能影响通过只统计 `images/` 与单表查询控制（5000 items / 数千图片规模下预计 < 2s）；
- 恢复工具中的“把孤儿文件重新挂载为图片记录”作为独立、显式的恢复动作，默认不启用。

## 9. Acceptance Sandbox

现状：
- `CLIPBOARD_SHELF_TEST_ROOT` 统一派生 DB/config/images/logs/backups/pet-tasks；
- `assertIsolatedRuntime()` 启动前硬校验（test 模式）；生产模式不再执行 guard（P0 修复）；
- fingerprint 快照（`scripts/acceptance-fingerprint.cjs`）；
- encryption-service / db-service 均按 TEST_ROOT 派生路径。

评估：
- **基本足够**：本阶段所有验收均证明生产 userData 零触碰；
- **残余缺口 1**：`CLIPBOARD_SHELF_USER_DATA`（旧环境变量）在非测试模式下仍会被 db-service / encryption-service 采纳且**无一致性校验**——生产环境一旦误设，会出现“DB/加密在一个目录、config/images 在另一个目录”的脑裂；建议改为仅测试模式有效，或在非测试模式下忽略并告警；
- **残余缺口 2**：验收 runner 仍是临时脚本（`release/_acceptance-tmp/*.cjs`、cdp 脚本），未纳入 `scripts/` 标准流程；建议 v1.9 把“创建 TEST_ROOT → fingerprint → 启动 → 断言全部路径 → 清理”固化为 `scripts/acceptance-runner` 系列（只读审查结论，不实施）；
- OCR 临时文件使用系统 temp（`os.tmpdir()`），可接受；
- 强杀进程会留下 TEST_ROOT 残留（本阶段多次发生），runner 需要“启动前清理上次残留”步骤。

## 10. 删除 / Retention 风险

| 操作 | 位置 | 当前保护 | 风险 |
| -- | -- | -- | -- |
| retention.run / cleanByPolicy | retention.js + db-service | Worksite/收藏保护 | 自动执行、无 dry-run、unlink 失败静默 |
| items:delete / batchDelete | ipc-handlers | UI 确认 | 单条有确认；批量有确认；unlink 失败静默 |
| clearNonFavorites | db-service + ipc | 收藏/现场保护 | UI 确认依赖调用方；无 dry-run |
| migration | db-service init | 幂等 + 启动前备份 | 备份可能含 WAL 缺口 |
| 图片 unlink | 上述全部 | 无 | **永久删除**，无回收站/软删除/删除前快照 |

**图片删除方案比较（v1.9 只评估，不实施）：**

| 方案 | 可靠性 | 复杂度 | 磁盘 | 恢复体验 | 结论 |
| -- | -- | -- | -- | -- | -- |
| 软删除（行标记 deletedAt） | 高 | 中 | 低 | 需 UI 支持 | P2 候选 |
| 系统回收站（shell.moveItemToTrash） | 高 | 低 | 低 | 原生体验 | **P1 候选（性价比最高）** |
| 删除前快照（移入 backups/trash/<ts>/） | 高 | 低 | 中 | 自建恢复 | P2 候选 |
| 保留 N 天 | 中高 | 中 | 中 | 需定时清理 | P2 候选 |

推荐：v1.9 先给所有图片 unlink 加 **dry-run 与失败日志**（P1），回收站化作为 P1/P2 边界，由后续版本决定。

## 11. 候选方向比较（评分）

| 方向 | 用户痛点 | 使用频率 | ROI | 技术复杂度 | 数据风险 | 与现有架构复用 | 新增 schema | 需要 AI |
| -- | -- | -- | -- | -- | -- | -- | -- | -- |

## 12. ROI 排序与 v1.9 推荐路线

### 排序

2. **P1 — Asset Integrity（只读诊断 + 报告）**

6. **P2 — Entity Search 增强（前缀 / 实时 Chip）**
7. **冻结 — AI Worksite / Document Index / Context Matching / 云同步 / RAG / Embedding**

### “完整备份”的定义（分析推导）

完整备份的最小充分集：

```text
完整备份 =
  ① DB 一致快照（SQLite backup API 或 wal_checkpoint 后拷贝，含全部业务表）
  ② config.json
  + pet-tasks.json
  + encryption.json（如存在）
  ③ 全部图片资产 images/full + images/thumb + images/annotated
  ④ Integrity Manifest（JSON）：
       - 生成时间 / 应用版本 / DB sha256
       - 每张图片：相对路径 / size / mtime / sha256 / 对应 item id（如可解析）
       - 校验规则版本
```

证明（缺一项会怎样）：
- 缺 ①：无数据；
- 缺 ②：设置丢失；缺 pet：仅宠物状态丢失（可接受但计入）；
- 缺 encryption.json：启用加密后**任何备份都无法解锁**（致命）；
- 缺 ③：恢复后只剩 metadata 空壳（本次事故形态）；
- 缺 ④：无法自动验证备份是否完整/损坏，恢复变成“赌”。

因此 ④ 不是可选项，是“可恢复”这一目标的校验层。

### 备份方案比较

| 方案 | 可靠性 | 速度 | 磁盘占用 | 恢复复杂度 | Windows 兼容 | 数据一致性 | 失败恢复 | 维护成本 |
| -- | -- | -- | -- | -- | -- | -- | -- | -- |
| A. 整目录复制（DB+images 按目录镜像） | 高 | 快（增量复制） | 随图片增长 | 低 | 高 | 取决于 DB 拷贝方式 | 中 | 低 |
| B. ZIP 快照 | 中高 | 慢（压缩） | 低 | 中 | 高 | 需先一致化 | 中 | 中 |
| C. DB 备份 + 图片资产清单（只记录不复制） | **低（图片不在备份内）** | 快 | 低 | 无法恢复图片 | 高 | 高（DB 部分） | 低 | 低 |
| D. Manifest + 增量资产备份 | 高 | 快 | 最低 | 中 | 高 | 高 | 高 | 高 |

**结论：** 纯 C 不能构成完整备份（清单不能代替文件）；纯 B 做主备份恢复复杂、增量差；D 最优但维护成本高。**v1.9 采用 A 的目录镜像 + C 的清单校验（A+C 混合）**：

```text
backups/YYYY-MM-DD_HHmmss/
  ├─ shelf.db            （SQLite backup API 一致快照）
  ├─ config.json
  ├─ pet-tasks.json
  ├─ encryption.json     （如存在）
  ├─ images/full|thumb|annotated/...（按清单复制）
  └─ manifest.json       （DB sha256 + 每文件 sha256/size/mtime + 行↔文件映射）
```

恢复 = 从快照目录整体校验 → 重建 userData → 运行完整性检查 → 二次确认。ZIP 导出可作为后续“便携导出”附加能力（P2）。

## 15. 数据模型建议

- **不需要新业务表**：备份 manifest 是文件（`manifest.json`），Asset Integrity 报告也是文件/控制台输出，不落库；
- 若未来做回收站：建议 `items.deletedAt` 软删除列 + `backups/trash/` 目录，v1.9 不实施；
- manifest 结构（v1 建议）：
  ```json
  {
    "version": 1,
    "appVersion": "1.8.0",
    "createdAt": 1234567890,
    "db": { "path": "shelf.db", "sha256": "…" },
    "config": { "path": "config.json", "sha256": "…" },
    "extraFiles": [
      { "path": "pet-tasks.json", "sha256": "…", "size": 296 },
      { "path": "encryption.json", "sha256": "…", "size": 55 }
    ],
    "images": [
      { "path": "full/xxx.png", "itemId": 123, "sha256": "…", "size": 12345, "mtime": 123 }
    ],
    "counts": { "items": 2717, "images": 207, "entities": 1839 }
  }
  ```
- Worksite 保持轻量、单归属；本版本不增加字段。

## 16. 性能要求

- 备份：5000 items / 数千图片规模下，全量快照目标 < 10s（异步、低优先级，不阻塞捕获主链路）；
- 图片复制用流式拷贝，manifest 哈希计算与拷贝合并单次遍历；
- Asset Integrity 只读巡检：目标 < 2s（仅统计 images 目录 + 单表查询）；
- 启动备份不拖慢启动（可延后 1-2s 或后台执行）；
- 禁止 N+1 查询；manifest 与 DB 行按 id 映射后单次比对。

---

## 17. 隐私要求

- 备份默认本地；可选对 manifest 不敏感（sha256 不含内容，可接受）；
- config.json 含 AI 密钥时，备份文件应标注“包含敏感配置”，导出（ZIP/人工拷贝）时默认脱敏或提示；
- 图片内容不进任何外部服务；恢复/巡检全程本地；
- 恢复操作必须二次确认，且只覆盖应用自身 userData；
- 巡检报告不输出正文内容，只输出文件名/计数/类型。

## 18. 测试要求

- 备份-恢复 roundtrip（备份 → 清空 → 恢复 → 完整性检查全绿）；
- manifest 校验失败注入（改一个字节 / 删一张图 → 恢复被拒绝或明确告警）；
- WAL 一致性测试（写入后强杀 → 启动备份仍含最新数据，验证 checkpoint/backup API 路径）；
- MISSING_FILE / ORPHAN_FILE 注入测试（Asset Integrity 输出正确分类）；
- 生产 userData 零触碰测试（备份/恢复/巡检全部在 TEST_ROOT 下执行）；
- 恢复后 FTS、加密解锁、worksite 关联、annotatedPath 有效性逐项断言；
- 全量回归保持 220+ 通过。

## 19. 风险

| 风险 | 等级 | 缓解 |
| -- | -- | -- |
| 备份覆盖/误恢复生产数据 | 高 | 二次确认 + 恢复前自动备份当前状态 + TEST_ROOT 验证 |
| WAL 不一致导致备份缺数据 | 高 | SQLite backup API 或 checkpoint 前置 |
| 图片量大导致磁盘翻倍 | 中 | 保留 N 份策略 + 后续增量（D） |
| 恢复后发现文件损坏 | 中 | manifest 校验先行，损坏则阻止恢复并报告 |
| 巡检误判（合法文件被当孤儿） | 低 | 只读 + 人工确认处置 |
| encryption.json 丢失 | 高 | 纳入备份清单 + 恢复检查 |

## 20. 最终结论

1. Clipboard Shelf = **本地优先的维修现场资料工作台 / 工作上下文入口**（不再是“剪贴板管理器”）；
2. v1.8 后最重要的数据资产 = **剪贴板正文/OCR 与图片本体**（文件资产是当前唯一不可恢复类别）；
3. 完整备份 = **DB 一致快照 + Config + pet-tasks + encryption.json + 全部图片 + Integrity Manifest**；
4. 当前 backup 最大漏洞 = **图片不进备份 + WAL 裸拷贝可能丢最近事务**；
5. Asset Integrity = **应该做**，且应先做只读诊断版（生产已实测 205 缺失 + 9 孤儿）；
6. v1.9 最值得做 = **Backup & Recovery**；
7. Backup / Recovery 排第一 = **是**（P0）；
8. 图文维修报告排第二 = **是**（P1）；
9. AI = **继续延后**（只保留图片工具内现有可选动作，不做 AI Worksite / AI 整理）；
10. 正式砍掉 = **Document Index、Context Matching、Toast 联想、云同步、RAG、Embedding**；型号前缀/实时 Chip 降 P2 暂缓。

**一句话：v1.9 的目标不是加功能，而是把用户已有的资产变成“可备份、可校验、可恢复”的资产。**
