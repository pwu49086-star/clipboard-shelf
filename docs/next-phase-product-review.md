# Clipboard Shelf 下一阶段产品复盘

> 状态：Product Review / 决策材料（非开发计划）
> 基线：v1.5.0（已发布、已冻结、正在实际使用）
> 原则：**减少功能增长，增加连接。**

---

## 1. 当前产品真实价值复盘

### 1.1 按链路逐环评估

```text
Clipboard → Capture → Source → Sensitivity → Storage → Search → Entity Recognition → Retention → Quick Actions
```

| 环节 | 现状 | 是否形成闭环 | 真实价值 |
|---|---|---|---|
| Capture | 1s 轮询，去重，异步落库 | ✅ | 高：核心，每天都在用 |
| Source | 前台应用/进程记录 | ⚠️ 半闭环 | 中：能看出“来自哪里”，但 ≤1s poll window 使其“不够可信”，用户不会把它当精确事实 |
| Sensitivity | 三级门禁，落库前决策 | ✅（保护性） | 高：防泄露，是信任基础，不是使用闭环 |
| Storage | SQLite + WAL + 加密 + 备份 | ✅ | 高：稳定基础设施 |
| Search | FTS5/LIKE + 时间/分类/标签 | ✅ | 高：最常用入口 |
| Entity Recognition | 落库后异步识别并持久化 | ❌ **未连接** | 目前对用户**零直接价值**：没有 UI、没有实体搜索、没有匹配消费方，是一条“修好但没通电的路” |
| Retention | maxItems/maxDays/图片上限/收藏保护 | ✅（维护性） | 中：防止膨胀，用户无感 |
| Quick Actions | 翻译/总结/解释/工单（AI）+ 复制/纯文本粘贴 | ⚠️ 半闭环 | 中：工单生成有价值，但藏在命令面板，且只吃“当前剪贴板单条文本”，不接历史/实体/多选 |

### 1.2 真正形成的闭环

1. **复制 → 记录 → 搜索 → 复制回剪贴板**（核心闭环，高频）
2. **复制 → 敏感门禁 → 安全落库**（信任闭环）
3. **复制 → AI 翻译/总结/工单**（低频但有价值的辅助闭环，依赖 API Key）

### 1.3 关键结论

- v1.5.0 的实体识别是**基础设施投资**，不是用户可感知功能；
- 当前最大的结构性问题是：**历史记录是一堆扁平的“碎片”，缺少组织、缺少连接、缺少出口**；
- 产品不缺“更多能力”，缺的是把已有能力接起来的“连接件”。

## 2. 能力分级：高价值 / 低价值 / 已验证无价值

### 2.1 高价值（已有，应强化）

| 能力 | 依据 |
|---|---|
| 剪贴板历史 + 搜索 | 每天使用，已稳定 |
| 敏感门禁 / 加密 | 专业用户的信任前提 |
| 来源（sourceApp） | 有帮助，但准确性不足以作为硬依据；可作为“线索”展示 |
| AI 工单草稿 | 与维修工作流强相关，当前入口太深、输入太窄 |

### 2.2 中价值（有条件才做）

| 能力 | 条件 |
|---|---|
| 实体识别 | 必须立刻接一个用户可感知的消费方，否则等于没做 |
| Document Index | 见第 4 节重估 |
| 便签 | 已有，但与剪贴板/工单工作流完全隔离 |

### 2.3 低价值 / 已验证无价值

| 能力 | 依据 |
|---|---|
| 数字键 + Enter 顺序粘贴 | 用户实机反馈：不实用 → **明确降级，不再迭代** |
| slice(0,200) 修复 | 影响观感，不影响核心流程；优先级最低 |
| WM_CLIPBOARDUPDATE | 准确性收益边际递减，用户能接受现状；继续暂缓 |
| Toast 联想（v1.5.2 原案） | 未验证、打扰风险高；在“实体可见性”和“文档召回”验证之前不该做 |
| Context Group / 上下文分组 | 概念好，但实现重、侵入 UI，当前没有足够证据支撑 |

## 3. 从真实工作流倒推产品

### 3.1 观察到的真实工作流（本用户）

用户是空调维修专业人员，实际高频行为：

```text
维修软件/微信/浏览器/IMA 复制故障信息
  → 粘贴到工作文档/聊天/Claude Code
  → 查维修手册（本地 PDF 文件夹，文件名本身有信息：大金/RXYQ系列/U4故障）
  → 整理 Evidence/KB/工单（多段复制内容拼装成结构化文档）
  → 让 AI 生成工单/总结
```

### 3.2 复制之后最常做什么（按频率倒推）

1. **粘贴到另一个窗口**（最高频，剪贴板本质是搬运）
2. **从历史里再找一段**（搜索/翻列表）
3. **把多段内容拼进一个文档/工单**（手工组装，重复劳动）
4. **去本地资料夹找对应手册**（文件名能对上，但每次都要手动开文件夹）
5. **让 AI 处理当前片段**（翻译/总结/工单）
6. 重新复制下一段（循环）

### 3.3 当前最明显的“断点”

**断点 1：历史是“碎片堆”，不是“工作现场”。**

一次维修任务里，用户会复制十几段内容（故障现象、型号、代码、聊天记录、手册片段），它们散落在历史列表里，无法“归到同一件事”。拼工单/报告时只能人肉翻找。

**断点 2：实体识别没有任何出口。**

“复制了 10 次 RXYQ16AYM/U4”这件事，产品完全不知道，用户也看不到。历史搜索只能靠全文 LIKE，不能回答“这台机型的故障记录有哪些”。

**断点 3：复制 → 资料文件的最后一跳是断的。**

文件名索引（v1.5.1）如果做，也只解决“找到文件”；但用户更常做的是“把内容组装成输出”（工单/报告/消息），这一跳目前完全靠手工。

## 4. v1.5.1（Local Document Index）重估

### 4.1 诚实评估

| 维度 | 评估 |
|---|---|
| 使用频率 | 中低：复制→找手册不是每次复制都发生；维修工一天可能 5–20 次 |
| 文件名召回 | 该用户资料夹命名良好，**文件名索引在其数据上召回可观**；但对一般用户不可控 |
| 实现成本 | 中高：目录配置、增量扫描、文件名实体提取、设置 UI、权限/路径异常 |
| 隐私/维护成本 | 中：扫描用户磁盘目录本身就是敏感行为；文件增删需要持续维护 |
| 与实体连接 | 可连接，但只到“文件名”级，正文索引是另一个大工程 |
| 对核心闭环的贡献 | 只多“一跳”提示，不改变“碎片堆”问题 |

### 4.2 结论

**原 v1.5.1 降级，不再作为下一版本默认首选项。**

理由：

1. 它解决的是“找到资料”，而当前更痛的是“把复制内容组织/输出成工作成果”；
2. 文件名索引收益对“命名良好的用户”成立，但不可复制到一般用户；
3. 在实体识别还没有任何用户可见出口之前，先做资料匹配属于“跳过接线、先造插头”；
4. 若未来要做，应作为“实体搜索/实体过滤”验证成功之后的第二步，且优先复用实体能力。

## 5. 候选方向

### 5.1 候选清单

| # | 方向 | 一句话 |
|---|---|---|
| A | 实体可见化 + 实体搜索/过滤 | 让 v1.5.0 的实体真正“通电”：列表展示实体徽标，点击/输入 `型号:RXYQ16AYM` 过滤历史 |
| B | 收集/多选导出 → 工单/报告草稿 | 选中多条历史 → 一键复制全部/导出文本/生成工单草稿 |
| C | 便签 × 剪贴板关联 | 把记录挂到一张便签/一个维修任务下，形成“工作现场” |
| D | Local Document Index（原 v1.5.1） | 文件名元数据索引 + 高置信联想 |
| E | 图片来源实体补全 | 截图/图片 OCR 后也走实体识别，图片可被实体搜索 |
| F | Toast 联想（原 v1.5.2） | 复制即提示本地资料数量 |

### 5.2 逐项评估

| 项目 | A 实体可见化 | B 收集→工单 | C 便签关联 | D 文档索引 | E 图片实体 | F Toast |
|---|---|---|---|---|---|---|
| 用户痛点 | 历史难按机型/故障归类 | 拼工单/报告靠人肉复制 | 一次任务的多段内容无法归拢 | 找手册要手动开文件夹 | 截图里的故障码搜不到 | 找资料少一步 |
| 使用频率 | 高（搜索是主入口） | 高（维修人员天天产出） | 中 | 中低 | 中 | 中低 |
| 实现复杂度 | 低（复用已有 entities + UI 过滤） | 中（多选已有，加导出/汇总） | 中高（新关系表/UI） | 中高 | 中（复用 OCR + entities） | 中（匹配+防骚扰） |
| 技术风险 | 低 | 低 | 中 | 中（扫描/权限） | 低 | 中（骚扰风险） |
| 现有架构复用 | 极高（entities 表即插即用） | 高（多选/剪贴板/AI 工单已存在） | 中（notes 已有） | 中（实体规则可复用） | 高（OCR 已有） | 中（依赖 D） |
| 是否需要新增数据库 | 否 | 否 | 是（小表） | 是（2 张表） | 否 | 否 |
| 是否需要 AI | 否 | 否（可选复用现有 AI） | 否 | 否 | 否 | 否 |
| 隐私风险 | 低 | 低 | 低 | 中（扫描目录） | 低 | 低 |
| ROI | **极高** | **高** | 中 | 中低 | 中 | 低 |

### 5.3 排序

1. **A：实体可见化 + 实体搜索/过滤**（激活已有投资，风险最低）
2. **B：收集/多选导出 → 工单/报告草稿**（直接减少高频重复劳动）
3. **C：便签 × 剪贴板关联**（为“工作现场”打基础，可后置）
4. E：图片来源实体补全（低成本增量）
5. D：Local Document Index（原 v1.5.1，降级）
6. F：Toast 联想（原 v1.5.2，暂缓）

## 6. 推荐的下一版本路线

### 建议：v1.6 = “把已有能力接起来”

**v1.6.0 —— 实体可见化与实体搜索**

- 列表行展示已识别实体（品牌/型号/故障码/制冷剂小徽标）；
- 搜索支持实体语法：`型号:RXYQ16AYM`、`故障:U4`、`品牌:大金`；点击实体徽标即过滤；
- 实体详情：点开某型号 → 该型号出现过的历史记录列表（复用 entities + items 查询）；
- 无新表、无 AI、无扫描，纯消费已有数据。

**v1.6.1 —— 收集与输出（工单/报告）**

- 多选记录 → “复制全部”“导出为文本/Markdown”；
- “生成工单草稿”：把选中记录按时间/来源拼接，复用现有 AI 工单动作（可选）；
- 直接对接用户现有“Evidence/KB/工单”文件工作流。

**v1.6.2（可选）—— 便签 × 剪贴板关联**

- 便签可“挂”相关记录；记录上下文菜单“附加到便签”；
- 为未来“任务/工作现场”概念打底。

### 路线原则

- 每一版都**让用户可感知地少做一步**；
- 优先**消费已有数据**（entities、notes、多选），而不是再造数据；
- Document Index / Toast / Context Group 全部后置到“实体搜索被高频使用”之后再验证。

## 7. 明确砍掉 / 暂缓清单

### 砍掉（不再迭代）

- 数字键 + Enter 顺序粘贴（用户实机判定不实用；代码保留不删）

### 暂缓（不进入下一版本）

- WM_CLIPBOARDUPDATE（准确性边际收益）
- Local Document Index（原 v1.5.1）
- Toast 联想（原 v1.5.2）
- Context Group / 任务分组大 UI
- slice(0,200) 修复（仅记录）
- 跨设备/云同步/浏览器扩展/WebDAV/RAG/Embedding（长期不做）

---

## 8. 决策原则（写进下一阶段）

进入下一版本的功能必须同时满足：

1. **高频**：在主工作流中每天至少被使用数次；
2. **减少操作步骤**：可量化地少做 1 步以上；
3. **复用现有能力**：优先消费 entities / notes / 多选 / AI / 剪贴板；
4. **不破坏稳定性**：不重构已冻结模块，不引入新依赖；
5. **可验证**：每一版都能用真实工作流验收。

> 终极目标不变：Clipboard Shelf 不是“功能更多的剪贴板”，而是“懂用户正在处理什么的本地工作上下文助手”。
